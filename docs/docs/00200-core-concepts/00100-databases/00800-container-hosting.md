Container Hosting runs a program in a [Docker](https://www.docker.com/) container alongside your database. The program connects to the database as the database itself, so your module can tell its calls apart from those of every client. Use it for work that a module can't do, such as long-running jobs, native code, and calls to network services like LLM APIs.

:::warning
***Container Hosting is a preview, and its configuration, commands, and behavior may change in upcoming SpacetimeDB releases. Maincloud doesn't run containers.***
:::

## How It Works

An image is a package that holds a program and everything it needs to run, such as its runtime and libraries. You build an image from a `Dockerfile`. A container is a running instance of an image.

You configure the container in [`spacetime.json`](../../00300-resources/00200-reference/00100-cli-reference/00300-spacetime-json.md), next to the module. When you run `spacetime publish`, the CLI publishes the module, builds the image, and attaches the container to the database. SpacetimeDB then runs it:

- **The container connects as the database.** SpacetimeDB gives the container a short-lived token for the database's [identity](../00500-authentication.md). When the container calls a reducer, the sender is the database, which no client can impersonate.
- **SpacetimeDB keeps the container running.** It starts the container, restarts it according to its [restart policy](#restart-policy), and stops it when you detach it or delete the database.
- **The container works like a client.** It's a separate process, so its work isn't part of a transaction. It changes the database only by calling reducers and procedures, and it reads the database by subscribing to tables.

Each database has at most one container.

Containers run on two kinds of servers. A local server is one that you run with `spacetime start`, usually on your own machine; it runs containers with the machine's Docker daemon. A hosted server is one that Clockwork Labs runs; during the preview, Clockwork Labs runs hosted servers with containers for preview participants. Maincloud doesn't run containers. [Servers and Networking](#servers-and-networking) describes how they differ.

### When to Use a Container

[Reducers](../00200-functions/00300-reducers/00300-reducers.md) can't reach the outside world. [Procedures](../00200-functions/00400-procedures.md) can make HTTP requests, but each request times out after at most 180 seconds, and a procedure can't keep state in memory between calls.

Use a container when you need to:

- Run work that takes longer than that, or runs continuously, such as an agent that works through a queue of tasks.
- Run native code, or libraries and tools that modules can't use, such as Python packages or `ffmpeg`.
- Talk to network services in ways other than a single HTTP request, such as streaming an LLM's response or holding a WebSocket open.
- Keep state in memory between tasks, such as a cache or a pool of connections.

For everything else, prefer reducers and procedures. They run inside the database, next to your data, and a reducer's changes are atomic.

## Quick Start

In this example, clients submit tasks to a database, and its container completes them. The container echoes each task's prompt back, or asks an LLM if you give it an OpenAI API key. Both the module and the container program are written in TypeScript.

You need:

- The [SpacetimeDB CLI](https://spacetimedb.com/install).
- [Docker](https://docs.docker.com/get-started/get-docker/), running: Docker Desktop on macOS, or Docker Engine on Linux.
- [Node.js](https://nodejs.org/) 22 or later.

The project has a module, a container program, and a `spacetime.json` that ties them together:

```text
my-agent/
├── spacetime.json
├── spacetimedb/          # The module
│   ├── package.json
│   ├── tsconfig.json
│   └── src/
│       └── index.ts
└── agent/                # The container program
    ├── .dockerignore
    ├── Dockerfile
    ├── package.json
    └── src/
        ├── main.ts
        └── module_bindings/  # Generated by `spacetime generate`
```

### Write the Module

Create `spacetimedb/package.json`:

```json
{
  "name": "my-agent-module",
  "private": true,
  "type": "module"
}
```

Create `spacetimedb/tsconfig.json`, with the compiler options that SpacetimeDB requires:

```json
{
  "compilerOptions": {
    "strict": true,
    "skipLibCheck": true,
    "moduleResolution": "bundler",
    "target": "ESNext",
    "lib": ["ES2021", "dom"],
    "module": "ESNext",
    "isolatedModules": true,
    "noEmit": true
  },
  "include": ["./**/*"]
}
```

Create `spacetimedb/src/index.ts`:

```typescript
import { schema, table, t, SenderError } from 'spacetimedb/server';

const spacetimedb = schema(
  {
    task: table(
      { public: true },
      {
        id: t.u64().primaryKey().autoInc(),
        prompt: t.string(),
        // 'pending' until the container completes the task, then 'done'.
        status: t.string(),
        result: t.string().optional(),
      }
    ),
  },
  {
    // Declared so that `spacetime publish` stores it from your shell.
    // Optional, so that the database works without it.
    env: { OPENAI_API_KEY: t.string().optional() },
  }
);
export default spacetimedb;

export const submitTask = spacetimedb.reducer(
  { prompt: t.string() },
  (ctx, { prompt }) => {
    if (prompt.trim() === '') throw new SenderError('prompt is empty');
    ctx.db.task.insert({ id: 0n, prompt, status: 'pending', result: undefined });
  }
);

export const completeTask = spacetimedb.reducer(
  { id: t.u64(), result: t.string() },
  (ctx, { id, result }) => {
    // Only the database's container calls as the database itself.
    if (!ctx.sender.isEqual(ctx.databaseIdentity)) {
      throw new SenderError('only the database container may complete tasks');
    }
    const task = ctx.db.task.id.find(id);
    if (!task) throw new SenderError(`task ${id} not found`);
    if (task.status !== 'pending') throw new SenderError(`task ${id} is already ${task.status}`);
    ctx.db.task.id.update({ ...task, status: 'done', result });
  }
);
```

Any client can call `submitTask`. Only the container can call `completeTask`, because its calls are the only ones whose sender is the database itself. [Restricting Reducers to the Container](#restricting-reducers-to-the-container) explains this check.

Install the module's dependencies. The CLI uses TypeScript to check the module when it builds it:

```bash
cd spacetimedb
npm install spacetimedb
npm install --save-dev typescript
cd ..
```

### Write the Container Program

Create `agent/package.json`. The program is bundled into a single file with [esbuild](https://esbuild.github.io/):

```json
{
  "name": "my-agent",
  "private": true,
  "type": "module",
  "scripts": {
    "build": "esbuild src/main.ts --bundle --platform=node --target=node22 --format=esm --outfile=dist/main.js"
  }
}
```

Create `agent/src/main.ts`:

```typescript
import { readFileSync } from 'node:fs';
import { DbConnection, tables, type ErrorContext } from './module_bindings';

// SpacetimeDB sets these in every container.
const uri = requireEnv('SPACETIMEDB_URI');
const database = requireEnv('SPACETIMEDB_DATABASE_IDENTITY');
const tokenFile = requireEnv('SPACETIMEDB_TOKEN_FILE');
// Set only if `env-keys` in spacetime.json lists it.
const openaiApiKey = process.env.OPENAI_API_KEY;

function requireEnv(name: string): string {
  const value = process.env[name];
  if (!value) exit(`${name} is not set; run this program in a SpacetimeDB container`);
  return value;
}

function exit(reason: string, error?: unknown): never {
  console.error(reason, error ?? '');
  process.exit(1);
}

DbConnection.builder()
  .withUri(uri)
  .withDatabaseName(database)
  // Read the token for every connection: each token expires after 10 minutes.
  .withToken(readFileSync(tokenFile, 'utf8').trim())
  .onConnect(conn => {
    // Runs for tasks already pending when the subscription starts, and for new ones.
    conn.db.task.onInsert((_ctx, task) => void work(conn, task.id, task.prompt));
    conn
      .subscriptionBuilder()
      .onError(ctx => exit('Subscription failed:', ctx.event))
      .subscribe(tables.task.where(task => task.status.eq('pending')));
    console.log(`Connected to ${database}`);
  })
  .onConnectError((_ctx: ErrorContext, error: Error) => exit('Unable to connect:', error))
  // Exit when the connection ends, so that SpacetimeDB restarts the program.
  .onDisconnect((_ctx: ErrorContext, error?: Error) => exit('Disconnected:', error))
  .build();

async function work(conn: DbConnection, id: bigint, prompt: string): Promise<void> {
  let result: string;
  try {
    result = openaiApiKey ? await complete(openaiApiKey, prompt) : `echo: ${prompt}`;
  } catch (error) {
    result = `error: ${error}`;
  }
  try {
    await conn.reducers.completeTask({ id, result });
  } catch (error) {
    // For example, an earlier run of this program already completed the task.
    console.error(`Unable to complete task ${id}:`, error);
  }
}

// Ask OpenAI's chat completions API.
async function complete(apiKey: string, prompt: string): Promise<string> {
  const response = await fetch('https://api.openai.com/v1/chat/completions', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${apiKey}` },
    body: JSON.stringify({
      model: 'gpt-4o-mini',
      messages: [{ role: 'user', content: prompt }],
    }),
  });
  if (!response.ok) throw new Error(`OpenAI returned ${response.status}`);
  const body = (await response.json()) as { choices: { message: { content: string } }[] };
  return body.choices[0].message.content;
}
```

The program connects to its database with the token that SpacetimeDB provides, subscribes to pending tasks, and completes each one by calling `completeTask`. When its connection ends, it exits with a nonzero code, and SpacetimeDB starts it again with a fresh token.

Create `agent/Dockerfile`, which builds the program in one stage and copies the bundle into a smaller image:

```dockerfile
FROM node:22-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY src ./src
RUN npm run build

FROM node:22-slim
WORKDIR /app
COPY --from=build /app/dist/main.js ./main.js
USER node
CMD ["node", "main.js"]
```

Create `agent/.dockerignore`, so that Docker doesn't copy installed packages into the build:

```text
node_modules
dist
```

Install the program's dependencies, which also creates the `package-lock.json` that the `Dockerfile` copies:

```bash
cd agent
npm install spacetimedb
npm install --save-dev esbuild
cd ..
```

### Configure the Database and Its Container

Create `spacetime.json` in the project's root directory:

```json
{
  "database": "my-agent",
  "server": "local",
  "module-path": "./spacetimedb",
  "generate": [
    { "language": "typescript", "out-dir": "./agent/src/module_bindings" }
  ],
  "container": {
    "build": "./agent"
  }
}
```

`container.build` names the directory with the `Dockerfile`. The `generate` entry tells `spacetime generate` to write the container program's bindings.

### Publish

Make sure Docker is running, then start a local server in a separate terminal, and leave it running:

```bash
spacetime start
```

The server checks for Docker once, when it starts. If Docker answers, the server runs containers, and it logs a line that says so. See [Local Servers](#local-servers) for the details.

In the project's root directory, generate the bindings and publish:

```bash
spacetime generate
spacetime publish
```

`spacetime publish` publishes the module, builds the image with Docker, and attaches the container to the database. It ends by printing the container's status:

```text
Created new database with name: my-agent, identity: c200...
Building container image spacetimedb-local/my-agent:latest for linux/arm64 from .../my-agent/agent
...
Container attached: sha256:47bd...
Container status: running
```

### Submit a Task

The CLI calls reducers by their names in snake case, so `submitTask` is `submit_task`:

```bash
spacetime call submit_task "Write a haiku about databases"
spacetime sql "SELECT * FROM task"
```

```text
 id | prompt                          | status | result
----+---------------------------------+--------+------------------------------------------------
 1  | "Write a haiku about databases" | "done" | (some = "echo: Write a haiku about databases")
```

If the task is still `pending`, wait a moment and query again. To see what the container is doing, run `spacetime container status`, or read its output with `docker logs` as described in [Logging](#logging).

Run `spacetime publish` again, and the container keeps running untouched, because nothing changed. Change the program, for example its echo text, and publish again: the CLI rebuilds the image, and since the image changed, it replaces the container.

### Call an LLM

To have the container ask an LLM, give it your OpenAI API key. Add `env-keys` to the container's configuration in `spacetime.json`:

```json
"container": {
  "build": "./agent",
  "env-keys": ["OPENAI_API_KEY"]
}
```

Then publish with the key in your shell:

```bash
OPENAI_API_KEY='sk-...' spacetime publish
```

The module declares `OPENAI_API_KEY`, so `spacetime publish` stores the key in the database's [environment](./00700-environment-variables.md). `env-keys` passes it to the container. The container's configuration changed, so `spacetime publish` restarts the container, which now completes tasks with the LLM's answers.

:::warning
For each environment key that the module declares, every `spacetime publish` reads the shell variable of the same name and stores its value in the database, replacing the stored one. If your shell exports `OPENAI_API_KEY` for other tools, every publish stores it. To publish without it, unset it first, for example with `env -u OPENAI_API_KEY spacetime publish`. The CLI prints the keys it sends and where each value came from.
:::

## Writing the Container Program

A container program can be written in any language and use any [client SDK](../00600-clients.md), or the [HTTP API](../../00300-resources/00200-reference/00200-http-api/00300-database.md). It connects to its database like any other client, with the address and token that SpacetimeDB provides.

### Variables Set by SpacetimeDB

SpacetimeDB sets these environment variables in every container:

| Variable | Value |
| -------- | ----- |
| `SPACETIMEDB_URI` | The URI of the SpacetimeDB API, as seen from the container, for example `http://host.docker.internal:3000`. Pass it to the SDK as the URI. |
| `SPACETIMEDB_DATABASE_IDENTITY` | The database's identity, in hexadecimal. Pass it to the SDK as the database name. |
| `SPACETIMEDB_TOKEN_FILE` | The path of a file that holds the container's token, `/run/spacetimedb/token`. |

The container also receives the database's environment variables that its [`env-keys`](#environment-variables-and-secrets) list.

### Connecting

Read the token from the file and pass it to the SDK, as you would any other token. Exit when the connection ends.

<Tabs groupId="client-language" queryString>
<TabItem value="typescript" label="TypeScript">

```typescript
import { readFileSync } from 'node:fs';
import { DbConnection } from './module_bindings';

const conn = DbConnection.builder()
  .withUri(process.env.SPACETIMEDB_URI!)
  .withDatabaseName(process.env.SPACETIMEDB_DATABASE_IDENTITY!)
  .withToken(readFileSync(process.env.SPACETIMEDB_TOKEN_FILE!, 'utf8').trim())
  .onConnectError((_ctx, error) => {
    console.error('Unable to connect:', error);
    process.exit(1);
  })
  .onDisconnect((_ctx, error) => {
    console.error('Disconnected:', error);
    process.exit(1);
  })
  .build();
```

</TabItem>

This program completes the quick start's tasks with the [Rust SDK](../00600-clients/00500-rust-reference.md). It assumes bindings generated with `spacetime generate --lang rust --out-dir src/module_bindings`.

```rust
mod module_bindings;

use module_bindings::*;
use spacetimedb_sdk::{DbContext, Table};
use std::{env, fs, process};

fn main() {
    // SpacetimeDB sets these in every container.
    let uri = env::var("SPACETIMEDB_URI").expect("SPACETIMEDB_URI is not set");
    let database = env::var("SPACETIMEDB_DATABASE_IDENTITY").expect("SPACETIMEDB_DATABASE_IDENTITY is not set");
    let token_file = env::var("SPACETIMEDB_TOKEN_FILE").expect("SPACETIMEDB_TOKEN_FILE is not set");
    // Read the token for every connection: each token expires after 10 minutes.
    let token = fs::read_to_string(token_file).expect("unable to read the token");

    let conn = DbConnection::builder()
        .with_uri(uri)
        .with_database_name(database)
        .with_token(Some(token.trim()))
        .on_connect_error(|_ctx, error| {
            eprintln!("Unable to connect: {error}");
            process::exit(1);
        })
        // Exit when the connection ends, so that SpacetimeDB restarts the program.
        .on_disconnect(|_ctx, error| {
            eprintln!("Disconnected: {error:?}");
            process::exit(1);
        })
        .build()
        .expect("unable to connect");

    conn.db.task().on_insert(|ctx, task| {
        let result = format!("echo: {}", task.prompt);
        if let Err(error) = ctx.reducers.complete_task(task.id, result) {
            eprintln!("Unable to complete task {}: {error}", task.id);
        }
    });
    conn.subscription_builder()
        .on_error(|_ctx, error| {
            eprintln!("Subscription failed: {error}");
            process::exit(1);
        })
        .subscribe(["SELECT * FROM task WHERE status = 'pending'"]);

    // Process messages until the connection ends.
    let _ = conn.run_threaded().join();
    process::exit(1);
}
```

### Token Lifetime

Each token is valid for 10 minutes, and SpacetimeDB writes a new one to the file every 5 minutes. A connection stays open after the token it was opened with expires, so a token only needs to be fresh when you open a connection or send an HTTP request.

Read the token file every time you connect or send a request, and never keep a token for later. A token is also only valid for the container's current [generation](#generations), a number that SpacetimeDB increases each time it replaces, starts, or restarts the container. When that happens, or the container stops, SpacetimeDB refuses the old token, and closes the connections that were opened with it within about a second.

The simplest pattern is the one in the examples above: exit with a nonzero code when the connection ends, and let the [restart policy](#restart-policy) start the program again, which then reads a fresh token. A program that reconnects without exiting must read the file again before each attempt. With the TypeScript SDK, you can do this with [`withAutomaticReconnect`](../00600-clients/00700-typescript-reference.md#method-withautomaticreconnect) and a [`withTokenProvider`](../00600-clients/00700-typescript-reference.md#method-withtokenprovider) that reads the file.

### Calling the HTTP API

To use the [HTTP API](../../00300-resources/00200-reference/00200-http-api/00100-authorization.md) instead of an SDK, send the token in an `Authorization: Bearer` header, reading the file for each request. The container's token also works for other databases on the same server, with the database as the sender. Calls to other databases aren't [internal](../00500-authentication/00600-authorization.md#internal-invocations), since their sender isn't the database being called.

### Logging

On a local server, the container runs in the machine's Docker daemon, so you can read its output with Docker:

```bash
docker ps --filter label=spacetimedb.supervisor
docker logs -f {name}
```

where _name_ is the container's name from `docker ps`, such as `stdb-1a2b3c4d-1-1`.

SpacetimeDB removes a container once its program exits, so the output of a program that crashed is gone. To keep a record, also have the program write what it does to the database, as described next.

On hosted servers, you can't read the container's output. To see what the container does, have it call a reducer that writes to a table, or that logs with `console.info` so that the message appears in [`spacetime logs`](../00100-databases.md#viewing-logs). `spacetime container status` shows when the program exits or fails to start.

## Restricting Reducers to the Container

The container calls reducers as the database itself, so their sender is the database's identity. No client can call with that identity, including the database's owner. Comparing the sender with the database's identity therefore tells you whether a call came from the container, or from one of the database's [scheduled](../00300-tables/00500-schedule-tables.md) functions.

Check it at the top of each reducer or procedure that only the container may call:

<Tabs groupId="server-language" queryString>
<TabItem value="typescript" label="TypeScript">

```typescript
if (!ctx.sender.isEqual(ctx.databaseIdentity)) {
  throw new SenderError('Only the database container may call this');
}
```

</TabItem>
<TabItem value="csharp" label="C#">

```csharp
if (ctx.Sender != ctx.DatabaseIdentity)
{
    throw new Exception("Only the database container may call this");
}
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
if ctx.sender() != ctx.database_identity() {
    return Err("Only the database container may call this".into());
}
```

</TabItem>
<TabItem value="cpp" label="C++">

```cpp
if (ctx.sender() != ctx.database_identity()) {
    return Err("Only the database container may call this");
}
```

</TabItem>
</Tabs>

These functions are public, so a client can still try to call them; the check rejects the call.

The container's calls are [internal](../00500-authentication/00600-authorization.md#internal-invocations), and they carry no JWT. In SDK versions that compute whether an invocation is internal from its sender, as [Authorization](../00500-authentication/00600-authorization.md) describes, `ctx.senderAuth.isInternal` in TypeScript, `ctx.SenderAuth.IsInternal` in C#, and `ctx.sender_auth().is_internal()` in Rust and C++ are equivalent to the comparison above. Earlier versions compute it differently and report the container's calls as not internal, so this page compares the identities directly.

:::note
Because the container acts as the database, its calls pass every check for the database's identity, and it can also call the database's private functions, such as scheduled reducers. Run only programs you would trust to act as the database.
:::

## Configuration

### `spacetime.json`

The `container` field of a database in [`spacetime.json`](../../00300-resources/00200-reference/00100-cli-reference/00300-spacetime-json.md#container-configuration) configures its container. It requires either `build` or an `image` pinned to a digest:

| Field | Default | Description |
| ----- | ------- | ----------- |
| `build` | | The directory with the `Dockerfile` to build, relative to `spacetime.json`. |
| `image` | | With `build`, a registry repository to push the image to. Without `build`, an image pinned to a digest. See [Images](#images). |
| `env-keys` | `[]` | The [database environment](#environment-variables-and-secrets) keys to set in the container. |
| `command` | The image's | The command to run, as an array of strings. It replaces the image's entrypoint and command. |
| `restart` | `"on-failure"` | When to restart the program after it exits: `"on-failure"`, `"always"`, or `"never"`. See [Restart Policy](#restart-policy). |
| `cpu-millicores` | `1000` | The CPU limit, in thousandths of a CPU. |
| `memory-bytes` | 1 GiB | The memory limit, as a number of bytes or a size like `"512MiB"` or `"1GB"`. There's no swap. |
| `scratch-bytes` | 1 GiB | The limit on the container's writable filesystem, including `/tmp`, as a number of bytes or a size. Only hosted servers enforce it. |
| `pids-max` | `512` | The limit on processes and threads. |
| `platforms` | `["linux/amd64", "linux/arm64"]` | The platforms to build for when pushing to a registry. |

For example, this container pushes its image to a registry, passes it an API key, and has 512 MiB of memory:

```json
{
  "database": "my-agent",
  "module-path": "./spacetimedb",
  "container": {
    "build": "./agent",
    "image": "ghcr.io/my-org/my-agent",
    "env-keys": ["OPENAI_API_KEY"],
    "memory-bytes": "512MiB"
  }
}
```

[Children](../../00300-resources/00200-reference/00100-cli-reference/00300-spacetime-json.md#children-and-inheritance) inherit `container` as a whole. A child can replace it, or set it to `null` to have no container.

Removing `container` from `spacetime.json` doesn't detach the database's container. Run `spacetime container remove` to detach it.

### Images

`spacetime publish` gets the container's image in one of three ways:

- **`build` without `image`.** The CLI asks the server for its platform, builds the image for it with `docker build`, and refers to it by its image ID, `sha256:{hex}`. No registry is involved: if the server doesn't have the image, the CLI uploads it into the database. A server has an image if the database stores it, or, for a local server, if its Docker daemon has it. A server at a loopback address, such as `localhost` or `127.0.0.1`, shares your machine's Docker daemon, so the CLI uploads nothing.
- **`build` and `image`, for a server that isn't at a loopback address.** The CLI builds the image for each of `platforms` with `docker buildx build --push`, pushes it to the repository that `image` names, and refers to it by its digest. Log in to the registry with `docker login` first. The server pulls the image without credentials, so the repository must be public. For a server at a loopback address, the CLI ignores `image` and builds locally.
- **`image` without `build`.** The CLI uses the image as it is. It must be pinned to a digest, like `ghcr.io/my-org/my-agent@sha256:{hex}`, or be an image ID, `sha256:{hex}`, which the CLI uploads like a build. Tags like `:latest` aren't accepted.

An image uploaded into the database is stored in the `st_container_image` system table, as the gzipped output of `docker save`. Uploaded images are limited to 256 MiB compressed, because a database keeps its tables in memory and in its commit log, and hosted servers allow less for some databases (see [Hosted Servers](#hosted-servers)). The server reports its limit, and the CLI checks the image against it before uploading. When you upload an image, the database keeps it and one other, the image its container uses, or else the newest, and deletes the rest. As the database's owner, you can list them with `spacetime sql "SELECT image_id, size, created_at FROM st_container_image"`.

To build for a server's platform, Docker may have to emulate it, for example to build a `linux/amd64` image on an Apple silicon Mac. Docker Desktop does this automatically.

The image must not declare `VOLUME` paths. A container whose image declares them fails to start.

### Environment Variables and Secrets

A container receives the values of the keys in `env-keys` from the database's [environment](./00700-environment-variables.md), which is where to keep secrets like API keys. It receives no other environment values. A container doesn't start if one of its keys has no value, and its status then reads ``failed: environment key `OPENAI_API_KEY` has no value``.

`spacetime publish` stores values in the database environment from two places:

- The `env` map of `spacetime.json`, or better for secrets, of a `spacetime.local.json` that you keep out of version control.
- Your shell, for each key that the module declares.

A key that only the container uses doesn't need a declaration in the module if you supply it in an `env` map. See [Supply Values When Publishing](./00700-environment-variables.md#supply-values-when-publishing) for the precedence rules.

Every `spacetime publish` stores the shell variables that have the names of keys the module declares, as the warning in [Call an LLM](#call-an-llm) explains.

The container reads its environment values when it starts, and SpacetimeDB restarts it when one of them changes. See [Publishing](#publishing).

### Restart Policy

The `restart` field decides what happens when the program exits:

| Policy | Restarts the program |
| ------ | -------------------- |
| `on-failure` | After it exits with a nonzero code, is killed for exceeding its memory limit, or is stopped because the machine or Docker restarted. An exit code of 0 means the program is done, and it stays stopped. |
| `always` | After every exit. |
| `never` | Never. |

SpacetimeDB waits before each restart, starting at 1 second and doubling up to 5 minutes. Once the program has run for 10 minutes, the wait starts over at 1 second. A restart keeps the container's [generation](#generations), so its token stays valid.

Each start uses a fresh filesystem, so keep state that must survive in the database.

### Managing the Container with the CLI

The `spacetime container` commands manage a database's container directly. In a directory with a `spacetime.json`, they act on its database; otherwise, pass the database's name or identity.

| Command | Description |
| ------- | ----------- |
| [`spacetime container status`](../../00300-resources/00200-reference/00100-cli-reference/00100-cli-reference.md#spacetime-container-status) | Shows the container's image, whether it should run, its generation, and its state. |
| [`spacetime container stop`](../../00300-resources/00200-reference/00100-cli-reference/00100-cli-reference.md#spacetime-container-stop) | Stops the container. |
| [`spacetime container start`](../../00300-resources/00200-reference/00100-cli-reference/00100-cli-reference.md#spacetime-container-start) | Starts the container, or restarts it if it's running. |
| [`spacetime container remove`](../../00300-resources/00200-reference/00100-cli-reference/00100-cli-reference.md#spacetime-container-remove) | Stops the container and detaches it from the database. |
| [`spacetime container set`](../../00300-resources/00200-reference/00100-cli-reference/00100-cli-reference.md#spacetime-container-set) | Attaches a container from an existing image, replacing the current one. |

`spacetime container status` prints something like:

```text
image:      sha256:4f9c...
desired:    running
generation: 1
restart:    OnFailure
state:      running
```

The state is one of `pending`, `starting`, `running`, `exited with code {code}`, `killed for exceeding its memory limit`, or `failed: {reason}`. `pending` means that the current generation hasn't reported a state yet, which is also what a stopped container shows.

`spacetime container set` sets the whole configuration from its flags: `--image`, `--env-key`, `--cpu-millicores`, `--memory-bytes`, `--scratch-bytes`, `--pids-max`, `--restart`, and a command after `--`. Flags you leave out take their defaults, and sizes are in bytes. It doesn't build or upload images, so `--image` must be pinned to a digest, or be an image ID that the server already has: one that the database stores, or, on a local server, one that its Docker daemon has.

If `spacetime.json` configures the container, the next `spacetime publish` replaces a container that you attached with `spacetime container set`. Use one or the other for a database.

Managing a container requires the same permission as publishing to the database. Viewing its status requires the permission to read the database's logs.

### HTTP API

The CLI uses these routes, under `/v1/database/:name_or_identity`:

| Route | Description |
| ----- | ----------- |
| `GET /container` | Returns the container's configuration, whether it should run, its generation, and its state. |
| `PUT /container` | Attaches a container, replacing the current one. |
| `DELETE /container` | Detaches the container. |
| `POST /container/start` | Starts the container, or restarts it if it's running. |
| `POST /container/stop` | Stops the container. |
| `GET /container/platform` | Returns the platform that images uploaded into the database must be built for, and the largest image the database accepts. |
| `HEAD /container/image/:image_id` | Answers `200 OK` if the database has the image, or the server is a local server whose Docker has it, and `404 Not Found` otherwise. |
| `PUT /container/image/:image_id` | Uploads an image into the database, as the gzipped output of `docker save`, up to the size that `GET /container/platform` reports. Answers `201 Created` if it stored the image, and `200 OK` if the database already had it. |

On a local server that runs containers only for clients on its own machine, `PUT /container`, `POST /container/start`, `GET /container/platform`, and both `/container/image` routes refuse other clients. See [Local Servers](#local-servers).

## Lifecycle

### Publishing

After `spacetime publish` publishes the module, it compares the container that `spacetime.json` configures with the database's current one:

- If the database has no container, it attaches one, which starts.
- If the configuration or image differs, it replaces the container, which restarts it with the new configuration.
- If nothing changed, it leaves the container alone, so that it keeps running. A container that had failed to start is restarted, in case the publish fixed the cause. A container whose program exited on its own isn't; run `spacetime container start` to run it again.
- If the container was stopped, it starts it.

SpacetimeDB also restarts a running container, under the same generation, when the database's value for one of its `env-keys` changes, for example because a publish stored a new one.

Pass `--no-container` to publish the module without building or attaching the container. If the CLI has to build an image, it checks that Docker answers before it publishes the module. If attaching fails after that, the module stays published; fix the problem and publish again. `spacetime dev` doesn't attach containers.

### Generations

A generation is a number that identifies one run of a database's container. SpacetimeDB takes a new generation when you attach a container, replace a running one, or start or restart it with `spacetime container start`, and when a running container's database is reset. Restarts under the [restart policy](#restart-policy) keep the generation.

A token is valid only for the current generation, and only while the container should run. Once a new generation starts, or the container stops, SpacetimeDB refuses the old token for new connections and requests, and closes the connections already opened with it within about a second. This keeps an old instance from acting as the database while it shuts down. Generations are never reused for a database identity, even after you delete the database and publish it again.

### Stopping

`spacetime container stop` sends the program `SIGTERM`, and kills it if it hasn't exited after 30 seconds. The program runs under a small init process, which passes the signal on. A stopped container stays stopped until you start it or publish again.

### Resetting and Deleting the Database

`spacetime publish --delete-data` resets the database. A running container stops while the database resets, then starts again as a new generation. The reset deletes the database's environment values, so supply the container's secrets again in the same publish (on a hosted server, see [Hosted Servers](#hosted-servers)); otherwise, the container fails to start until you publish them. The reset also deletes the images uploaded into the database, so `spacetime publish` uploads the image again if the server needs it.

`spacetime delete` deletes the database, with its images, and its container.

On hosted servers, a container doesn't run while its database is paused or suspended, and starts again as a new generation when the database resumes.

## Servers and Networking

### Local Servers

A local server runs containers with the machine's Docker daemon if Docker answers when the server starts. If you start Docker later, restart the server. By default, it accepts containers only from clients on the same machine: requests from other machines, or from web pages, to attach, start, or upload a container fail with `403 Forbidden` and a message that explains how to allow them. This is because anyone who can reach a local server can create a database, and local containers aren't isolated from your machine's network. To accept containers from other machines, start the server with `--enable-containers`, or set `enabled = true` in the [`containers`](../../00300-resources/00200-reference/00100-cli-reference/00200-standalone-config.md#containers) section of the server's `config.toml`. To run no containers, use `--disable-containers`, or `enabled = false`. The flags override `config.toml`, which also sets the Docker host and the URI that containers use to reach the server.

The server finds Docker through the `DOCKER_HOST` environment variable, or else Docker's default socket. If Docker Desktop's **Allow the default Docker socket to be used** setting is off, start the server with `--container-docker-host unix://$HOME/.docker/run/docker.sock`.

On Linux, containers reach the server through Docker's bridge network, so the server must listen on every address, as it does by default (`0.0.0.0:3000`). If it listens on a specific address instead, such as `127.0.0.1:3000`, then by default it runs no containers unless you set `api-url` in `config.toml`, or pass `--container-api-url`, to a URL that containers can reach.

Local containers are for development:

- A container can reach the Internet, your local network, and, through `host.docker.internal`, every service on your machine.
- Nothing can connect to a container from outside, since no ports are published.
- CPU, memory, and process limits apply, but `scratch-bytes` doesn't.

If you stop the server, its containers keep running, and the next `spacetime start` with containers enabled takes them over. Containers left over from a server that runs without containers keep running unsupervised, and their tokens stop working. To remove the containers of every local server on the machine, run:

```bash
docker rm -f $(docker ps -aq --filter label=spacetimedb.supervisor)
```

### Hosted Servers

On a hosted server, an identity can attach containers to its databases only after Clockwork Labs grants it access; until then, the server answers ``Permission denied: {identity} may not publish containers``.

Containers on a hosted server are isolated:

- **Outbound:** the container can connect to the Internet and to the SpacetimeDB API at `SPACETIMEDB_URI`.
- **Blocked:** private, shared, loopback, link-local, multicast, and reserved addresses, including cloud metadata services, as well as other containers and every other service on the server.
- **Inbound:** nothing can connect to the container.
- **Limits:** every limit applies, including `scratch-bytes`. The server rejects a container whose limits exceed what it allows, or what it has free.
- **Uploaded images:** a database with more than one replica stores uploaded images of at most 32 MiB, because replication sends each image to the other replicas in one message. Push larger images to a registry.
- **Image IDs:** a hosted server runs an image by its ID, `sha256:{hex}`, only if the database stores it. It doesn't use an image just because its Docker daemon has it, since that daemon also holds other databases' images.

During the preview, a hosted server doesn't accept environment values in the publish that creates or resets a database. For a new database, `spacetime publish` handles this: it publishes the module without them, then stores them, as `--env-only` does, before it attaches the container. The module's `init` reducer runs without them. A reset with `--delete-data` that sends environment values fails with `environment control operation unavailable`. To start over, delete the database with `spacetime delete` and publish again.

## Current Limitations

- A database has at most one container.
- On hosted servers, you can't read a container's output or open a shell in it.
- Nothing can connect to a container, so it can't serve requests. The `--port` flag of `spacetime container set` has no effect.
- A server pulls images from registries without credentials, so images in registries must be public.
- An image uploaded into the database is limited to 256 MiB compressed, or 32 MiB for a database with more than one replica on a hosted server.
- On hosted servers, `spacetime publish --delete-data` fails if it sends environment values. Delete the database and publish again instead. See [Hosted Servers](#hosted-servers).
- An image ID depends on Docker's image store. If your Docker daemon and the server's use different image stores (the classic store, or containerd), the server can't load an uploaded image under the same ID, and the container fails to start. Push the image to a registry instead, with `build` and `image`.
- `spacetime dev` doesn't build or attach containers.
- Containers on a local server have been tested on macOS with Docker Desktop and on Linux with Docker Engine, but not on Windows.
- Maincloud doesn't run containers.
