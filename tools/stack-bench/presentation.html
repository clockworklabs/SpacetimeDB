Stack Bench

Stack Bench measures whether the backend an AI agent ships actually works.

Stack Bench has an agent build a real-time store, then attacks the result the way production would. Every failure is found by using the app, and every fix lands on the bill.

what is measured

Same app. Same model. Different database.

One agent builds the same storefront over and over. The prompt, the requirements and the model stay pinned; the database underneath is the only thing that changes.

the harness

What actually runs

The agent builds inside a sealed container, with the grader on the other side of the wall. The grader drives the deployed app through real browser contexts and emits one typed verdict per criterion. Failures travel back up the dashed edge as customer-facing descriptions for the next fix round.

why the bill differs

Either the database keeps the count, or your code keeps it

what the agent writes
one call, and it holds
▲
database
serialises the write itself
✓ correct however the agent writes it
what the agent writes
open a transaction
lock the row
re-check the stock
commit, or retry
▲
database
offers the pieces, leaves the rule to you
correct while every piece is right ✗ one piece missed → sold twice

That is the whole bet. On one side the database owns the rule, so the agent gets it right by default. On the other the agent assembles the rule itself, and every piece it has to remember is a piece that can go missing, at a cost that shows up in the bill.

proving the grader

The grader earns the right to score

checkout→ guard: stock ≥ 1→ decrement→ commit
mutation removes the guard from a fully passing app
criterion no-oversellfails · kill confirmed
every other criterionstill passes · clean kill
blank app, full suiteholds at zero

A criterion earns the right to score once it catches a defect planted in a passing app, hits exactly the criterion it declared, and holds an empty build at zero. A planted defect that survives points at the grader, and the criterion goes back for repair.
