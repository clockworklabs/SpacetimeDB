Technical reference

StackBench

Each agent builds an online store from a feature list on one stack, and StackBench scores how many of its features hold up under production conditions.

Code from commit 6c65947996.

01How it is set up

HostOne machine running Docker. Every part of StackBench is a Docker container on it.
ControllerStackBench itself, written in TypeScript on Node.js. Docker Compose starts it as a container on the host's network, with the host's Docker socket mounted, so it can start and stop the other containers.
Each runA new Docker bridge network and a set of containers on it, which the controller creates for the run and removes afterwards.
Coding containerNode.js 22 on Debian with git and Chromium, plus the agent CLIs: Claude Code, Codex, Grok CLI, and Antigravity.
DatabasesPostgreSQL 16, MongoDB 7, Convex's self-hosted backend, Supabase (Postgres, GoTrue, PostgREST), and the Spacetime standalone server, compiled from this repository at the release commit.
Firewallnftables rules loaded into the run's network.
BrokerA Node.js HTTP proxy in its own container on the run's network.
BrowserChromium in its own container on the run's network. The grader in the controller container uses Playwright 1.62, which starts Chromium inside the browser container with docker exec and sends it commands over that connection's input and output. Chromium then opens the store over the run's network.
Package cacheVerdaccio, a private npm registry that mirrors the public one.

Controller

  • The controller container runs outside the run's network, so the agent cannot reach the checks, the grader, or the API keys.

Coding container

  • Everything except the store code is read-only.
  • The agent has no web search and cannot start sub-agents.
  • The agent can run Chromium in its container to test its own work.

Broker

Holds the API key so the agent never sees it.

  • A request that could push the run past its spending cap is refused.

Network

  • Each run has its own private network. The agent can reach public websites and the package cache, but not the host or other runs.
  • Downloading StackBench's own source from the web voids the run.

02How the store is tested

Playwright

Playwright is a library that drives a real browser from code. StackBench uses it to click, type, and read the store's pages the way a customer would.

  • Chromium has no open port, so nothing on the run's network can control it.
  • Each simulated customer gets a fresh browser, so no two share a session.
  • Test accounts get new names on every run.

How checks find things

The agent designs the store freely, but the prompt lists the IDs StackBench reads, such as the buy button or the stock count.

  • The IDs fix names only, not layout, data model, or libraries.

Example check: back-in-stock alert

  1. Stock to 0written to the database
  2. Request alertas the customer
  3. Stock to 1written to the database
  4. Wait 75 s
  5. Sign in freshnew browser
  6. Expect alertwithin 15 s
  • The 75-second wait leaves room for a store that checks stock once a minute.

Direct server requests

Some checks skip the page and call the server directly, to test rules a page could simply hide, such as who may change an order.

  • Requests use the signed-in customer's own session.
  • A refusal only counts after StackBench has seen the same request succeed, so a missing endpoint cannot pass as a permission check.

Outside database writes

Some checks change stock directly in the database, the way another system would, and see whether the store notices.

  • The prompt requires stock in a table that the database's own tools can update.
  • StackBench writes with each database's normal client.

Restarts and crashes

  • A restart stops and starts the store normally.
  • A crash test kills the store server or the database process with SIGKILL. On Spacetime, Convex, and Supabase the database is the server, so the database is killed.

Lost replies

The server saves a write, but the reply never reaches the browser, as on a dropped connection.

  • The store must still end up with one order.

Data leaks

A page can hide data the server still sends.

  • StackBench records every message the server sends each browser and searches those messages for other customers' data.

03A run, start to finish

Features come in levels, and each level is one agent session.

  1. Promptthis level's features
  2. Agent builds
  3. Log auditchecks what it read
  4. Snapshotsaves the store code
  5. Clean startrestores and restarts
  6. Run checksempty database per group
  7. Unlockpassed features open the next level

Agent session

  • Every stack gets the same prompt except its stack setup. Spacetime's setup also includes its SDK reference.
  • The production checks, such as permissions, live updates, and restarts, are never written into the prompt.
  • A session ends when the agent says it is done, or after 2 hours.

Log audit

  • After every session StackBench reads the agent's log. A run that read StackBench files or downloaded StackBench source is thrown out.

Clean start

  • Grading fails if startup changes the saved code, so the graded code is exactly what the agent wrote.

Empty database for each check group

  • Checks are grouped by file, and each group starts on an emptied database and a freshly started store.
  • If StackBench cannot measure a check, the group runs once more. If it still cannot, the run is thrown out and redone.

Unlocking features

A feature unlocks the features built on it only when all its checks pass.

  • The agent never sees its results and gets no second try.

04How we know the checks work

Three controls

Before a check is trusted, StackBench runs it on every stack against three stores.

Reference storeA correct store. Every check must pass.
One seeded bugThe reference store with one small break, once per bug. Its checks must fail and the rest pass.
Empty siteA blank page. Every check must fail.
  • Each seeded bug is a small edit listed with the checks that must catch it.
  • A stack's results are published only after all three controls pass.

05Time, rate limits, and cost

Time limits

  • Sessions last up to 2 hours and runs up to 4 hours, not counting time waiting to be graded.
  • A run that hits a limit or the spending cap is thrown out and redone.

Rate limits

  • When a provider rate-limits the agent, StackBench waits 1, 2, then 5 minutes. If it is still limited, the run pauses until an operator resumes it.

Cost

Cost is model usage priced at public API rates from the tokens the provider reports.

  • A request with no reported usage counts at its maximum possible cost, which makes the run's cost an upper bound.

06Hard questions

How is this set up?

Everything is a Docker container on one machine. The controller container runs StackBench. For each run it creates a private Docker network with four containers: the database, the agent's coding container, a broker that holds the API key, and Chromium. The controller stays outside that network and grades the store by driving Chromium with Playwright.

How is it graded automatically?

After each session StackBench restarts the store from its saved code, empties the database for each check group, and drives a real browser through every check.

How can fixed checks find things in a store the agent designed?

The prompt lists the IDs StackBench reads. They fix names only, not layout or code.

Can the agent see or game the checks?

No. The checks live outside the run, test accounts get new names every run, and a run that reads or downloads StackBench files is thrown out.

Can the agent test its own work?

Yes. It can run Chromium and its database inside its own container.

Could leftover state from the build fake a pass?

No. Grading wipes the code, restores the saved code, starts cold, and fails if startup changed the code. Each check group starts on an emptied database.

How do you know a failure is the store's fault?

Each check passes on that stack's reference store, catches its seeded bugs, and fails on an empty site. Checks read only the listed IDs, so a different design passes as long as it behaves correctly.

What counts as a measurement problem?

Anything that stops StackBench from deciding pass or fail, such as a refusal from an endpoint it never saw succeed. Those runs are thrown out and redone, never scored.

Why are the production checks left out of the prompt?

Customers never write "don't show me other people's orders". If the prompt listed every requirement, StackBench would only measure whether agents follow instructions.

Why does one failed check block later features?

Later features build on earlier ones. A checkout built on a cart that loses writes inherits the bug.

Does Spacetime get an advantage?

Its stack setup includes the Spacetime SDK reference, and the other stacks get connection details only. Results describe each stack as an agent receives it.

Is writing straight to the database fair to Convex and Spacetime?

The prompt requires a stock table the database's own tools can update, and every stack's reference store passes these checks.

Does the live-update requirement favor real-time databases?

Every stack's reference store passes every live check, and polling counts if the page updates within 10 seconds. Most failing stores never refresh the page at all.

What happens when a run hits a time limit or the spending cap?

It is thrown out and redone.

Clockwork Labs makes Spacetime. Why trust the results?

StackBench is developed by Clockwork Labs, Convex, and Emergent. Spacetime (Clockwork Labs) and Convex are both included on the leaderboard. Every stack gets the same feature list and the same checks, and each stack's checks are proven on its own reference store.

Did every model get the same prompt?

Yes, apart from the stack setup.

Can we read the code?

Yes. Every code chip links to the exact lines in the SpacetimeDB repository on GitHub.
