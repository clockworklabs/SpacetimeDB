Technical reference

StackBench

Each agent builds an online store from a feature list on one stack, and StackBench scores how many of its features hold up under production conditions.

Code citations are from StackBench commit 6c65947996.

01How it is set up

HostOne Linux machine running Docker, which runs each part of StackBench in its own Docker container.
ControllerThe container that runs StackBench itself and starts every other container.
  • Written in TypeScript on Node.js
  • Uses the host machine's network directly, so it sits outside every run's private network
  • Has the host's Docker socket mounted, which lets it create, enter (docker exec), and remove the other containers. That is full control of Docker on the machine, which is why the firewall makes it unreachable from every run
Each runA private network with four containers, or ten on Supabase, created when the run starts and removed when it ends.
  • The database container is created first, on a new Docker bridge network
  • Every other container joins the database container's network (--network container:<database>), so they all share one set of addresses and one firewall, and reach each other on localhost
Coding containerBuilt from node:22-slim (Debian). It has 2 CPUs, 4 GB of memory, and a limit of 2,048 processes, and includes:
  • git
  • Chromium
  • Puppeteer Core: Google's Node.js library for controlling Chromium, used only by the agent to test its own store
  • The agent CLIs, each fixed to one version: Claude Code 2.1.284 (Anthropic), Codex 0.159.3 (OpenAI), Grok CLI 1.0.46 (xAI), and Antigravity 1.3.2 (Google)
DatabasesEach stack runs one exact build:
  • PostgreSQL: the postgres:16 image
  • MongoDB: the mongo:7 image
  • Convex: Convex's self-hosted backend image
  • Supabase: seven images (Postgres, GoTrue for sign-in, PostgREST for the data API, Realtime, Storage, Edge Runtime, and an Envoy gateway)
  • Spacetime: the SpacetimeDB server, compiled from the SpacetimeDB repository at the same commit as StackBench
  • Every image is pinned by its sha256 digest, a fingerprint of its exact contents, so every run gets a byte-identical copy
FirewallEach run's network can reach the internet over HTTP and HTTPS, the package cache, and its own containers. It cannot reach the host, the controller, or other runs.
  • Written as nftables rules, the Linux kernel's packet filter, which apply to every container in the run
  • Allowed: the run's own containers (localhost)
  • Allowed: replies on connections already open
  • Allowed: the package cache on port 4873
  • Allowed: TCP ports 80 and 443 to public IPv4 addresses
  • Rejected: the host's addresses, every private and reserved IPv4 range, and all IPv6
BrokerA Node.js HTTP server in its own container on the run's network. It holds the model provider's API key and stops the run's spending at the cap.
BrowserChromium in its own container on the run's network, so it opens the store at the same localhost address the agent used.
  • Playwright 1.62.1 in the controller starts Chromium inside this container with docker exec, and sends it commands through that docker exec process
  • Chromium opens no network port, so no other container in the run can connect to the grading browser
Package cacheVerdaccio, a private npm mirror shared by all runs on the machine. Every run installs npm packages through it, so each package is downloaded from the public registry once per machine.

Coding container

This is where the agent works. It can write and run the store's code and reach the internet, but it cannot modify the system files that grading later runs the store on, and it cannot reach the host, the controller, or other runs.

  • Restrictions:
    • System files are read-only (--read-only), so the agent cannot change the tools and libraries grading relies on
    • No Linux admin privileges (--cap-drop ALL), except six file and process permissions added back: CHOWN, DAC_OVERRIDE, FOWNER, KILL, SETGID, and SETUID
    • No way to gain more privileges later (no-new-privileges)
  • What the agent can write to:
    • /app, the store's code, which is a folder on the controller mounted into the container
    • Temporary folders and the agent's home folder, which are erased with the container
    • The CLI's log folder
    • On Spacetime, the SDK and the spacetime command are mounted read-only
  • The CLIs' built-in web search tools are off. Sub-agents are refused, because the log audit cannot yet see what a sub-agent does. The agent can still reach websites from its shell, for example with curl, and the log audit flags any StackBench address that appears in its commands.

Broker

The agent's CLI needs an API key to call its model, such as an Anthropic or OpenAI key, or the login token of a Claude or ChatGPT plan. If the agent could read that key, it could copy it or spend past the run's cap of $100. So the key stays in the broker, and the CLI is given only the broker's localhost address and a random session token.

  • For each request from the CLI, the broker:
    • Refuses it unless it carries the session token
    • Reserves the most the request could cost: its size in bytes counted as input tokens, which is always more than the real count, plus the maximum output tokens the request allows
    • Refuses it with HTTP 402 if the run's spending, plus requests still in flight, plus this maximum would pass the cap
    • Otherwise removes the CLI's auth headers, adds the provider's API key, and forwards it over HTTPS
    • When the reply arrives, replaces the reservation with the cost of the tokens the provider reports
  • Where it forwards requests:
    • Anthropic: api.anthropic.com
    • OpenAI: api.openai.com, or chatgpt.com for a ChatGPT plan
    • xAI: api.x.ai, or cli-chat-proxy.grok.com for a Grok plan
    • Google: generativelanguage.googleapis.com, or daily-cloudcode-pa.googleapis.com for a Google plan
    • OpenRouter: openrouter.ai

02How the store is tested

Playwright

Most checks use the store the way a customer does: they open its pages in a browser, click, type, and read what the page shows. Playwright is the Node.js library StackBench uses to do this from code. Some checks also call the server directly, write to the database, or restart and kill processes.

  • Each simulated customer gets a separate browser profile (a Playwright browser context), so customers never share cookies or sign-ins.
  • Every test account name gets a suffix unique to the run, so a store cannot recognize test accounts by name.

How checks find things

Every agent designs its own store, so a check cannot find a button by its position or its label. Instead, the prompt lists a name for each element the checks use, such as notifications-toggle for the button that opens notifications, and the agent must put that name on the element.

  • The agent sets the name as the element's id, or as its data-role attribute when the element repeats, such as one per order.
  • StackBench finds the element with the CSS selector [data-role="name"],#name.
  • Apart from these names, the server operations, and the stock, order, and cart tables the prompt requires for direct reads, the agent chooses everything: layout, wording, its other tables, libraries, and how the browser talks to the server.

Example check: back-in-stock alert

A customer asks to be alerted when an out-of-stock item returns. StackBench then puts the item back in stock by writing straight to the database, the way a warehouse system would, and checks that the alert reaches the customer.

  1. Stock to 0database write
  2. Request alertcustomer clicks
  3. Stock to 1database write
  4. Wait 75 s
  5. Sign in againin a new browser
  6. Alert shownwithin 15 s
  • Checks are written as JSON lists of steps. Each step is an action, such as dbSetStock, wait, click, or expect, and each has a time limit.
  • An expect step keeps rechecking the page until it matches or its time runs out, here 15 seconds.
  • The 75-second wait allows for a store that looks for restocks in a background job once a minute.
  • Signing in again in a new browser tests that the alert is stored with the customer's account, so it still shows after the original page is gone.

03Production checks

Production checks put the store through conditions the prompt does not describe, such as a crash, a second customer, or a lost reply. Some rely on a rule the prompt does state, for example that start.sh may run again; what the prompt leaves out is the condition the check creates. Every step below is run by StackBench in the controller container, through Playwright in the run's Chromium container, through docker exec into the run's containers, or with HTTP requests to the store. A check can end three ways: passed, failed, or undecided. Undecided means StackBench could not reach a pass or fail: its own tooling failed, such as a browser crash, or the moment a check had to observe had already passed, such as a scheduled job coming due during a slow restart. An undecided check file is run once more, and if it is still undecided the whole run is left out of scores.

Saved data survives a restart

A store can keep data, such as a cart or a saved address, in its server's memory. It works until the server restarts for an update, and then the data is gone.

What StackBench does

  • Playwright, signed in as a customer, fills in and saves a delivery address on the store's profile page, reloads the page, and confirms the address shows.
  • StackBench then restarts the process that runs the store's own code, with docker exec into the container that runs it:
    • PostgreSQL and MongoDB: the store's Node.js server. StackBench sends SIGTERM to the recorded process group, waits up to 10 seconds for it to exit, and sends SIGKILL if it has not. It then runs the store's start.sh again in the coding container, waits up to 15 minutes for the store's port to answer with HTTP 2xx, and requires exactly one process listening on it
    • Supabase: the same restart of the store's own server. A Supabase store's server operations are Postgres functions, which keep no state of their own between calls, so the Node.js server the agent wrote is the only place a Supabase store's code could hold data in memory
    • Spacetime: the SpacetimeDB server, where the store's module runs. StackBench sends SIGTERM to the recorded process group, waits up to 10 seconds for it to exit, and sends SIGKILL if it has not, waits up to 30 seconds for /v1/ping to stop answering, starts the server again on the same data folder, and waits up to 60 seconds for /v1/ping to answer
    • Convex: the Convex backend process, where the store's functions run. The same stop, then a restart on the same data file, waiting up to 60 seconds for /version to answer
  • Playwright then opens a new browser context, with no cookies or storage from before, signs in as the same customer, and opens the profile page.

Passes when

  • The saved address shows in the new browser context.
  • A store that does not come back up within those limits fails. If StackBench's own restart command fails, the check is undecided.

Why it is a fair test

  • A reload alone can pass from data the browser kept, so only a restart plus a new browser context proves the server stored the data.
  • Each stack's restart hits the process where the agent's code can hold data in memory: the store's server on PostgreSQL, MongoDB, and Supabase, and the database process on Spacetime and Convex, where the agent's module or functions run. On PostgreSQL, MongoDB, and Supabase the database holds no code that can keep data in memory, so restarting it would test nothing the agent wrote. The checkout crash check kills those databases instead.
  • start.sh being run again is in the prompt: it says the environment can run start.sh again with APP_WARM_START=1, which only allows reusing installed packages, and that existing data must be preserved.

What it does not prove

  • Behavior on power loss or disk corruption, or on a sudden kill. This check stops processes with SIGTERM first; the checkout crash check kills them with SIGKILL and no warning.

Follow-ups

Does the store know it is being restarted?
It sees what any deploy looks like: its process stops and start.sh runs again with APP_WARM_START=1. The prompt tells every agent in advance that this can happen.
What about Supabase Edge Functions, which run in another container?
That container is not restarted. None of the 39 Supabase stores in the archived studies contains any Edge Function code, so no result depends on it.
What if an agent puts logic in a separate server on Spacetime or Convex?
That server is not restarted, because the store's code is expected to run in the database. One of 45 saved Spacetime stores runs a timer in its web server, and it only calls a reducer that reads pending work from the database, so it behaves the same either way.

Other customers' requests are refused

A store can hide the cancel button on other customers' orders and still cancel any order whose request reaches its server. Anyone who copies the request from the browser's developer tools can then act as someone else.

What StackBench does

  • The prompt gives the exact server operation for each feature: an HTTP method and path such as POST /api/cart on PostgreSQL and MongoDB, a named reducer on Spacetime, a named mutation on Convex, or a named Postgres function on Supabase.
  • First an allowed user performs the operation, for example an admin restocking an item, and it must succeed. This proves the operation exists and that the request StackBench sends is well formed.
  • StackBench then sends the same request as a user who must be refused, with Node.js fetch from the controller container or, for the cross-site case, from a real browser page, using one of:
    • That user's own session: the Authorization header and cookies copied from their signed-in browser context
    • No session at all
    • A session whose token has one character of its signature changed
    • A real browser page served from a different origin, so the browser's SameSite and cross-origin rules decide which cookies are sent
  • Or StackBench takes a write the store's own page sent, which Playwright recorded, swaps in another customer's id such as their order number, and sends it with the attacker's session.
  • Checks that guard stored data then read the database to confirm nothing changed, such as stock or purchases.

Passes when

  • The store refuses: HTTP 400, 401, 403, 409, or 422, a 404 once the operation is proven to exist, a failed reducer on Spacetime, a ConvexError on Convex, or a Postgres error on Supabase.
  • The check fails if the request is accepted, or if the server answers with an error such as HTTP 500, because a crash is not a refusal.
  • If the allowed user's request never succeeded, nothing proves the route exists, so a refusal cannot count and the check fails at that step.

Why it is a fair test

  • Hiding a button says nothing about what the server accepts, so the check talks to the server directly.
  • Because the same request first succeeds for an allowed user, a refusal for the attacker cannot be blamed on a malformed request.

What it does not prove

  • Protection against SQL or NoSQL injection, or endpoints the prompt does not list.

Follow-ups

How does StackBench know where the endpoint is when the agent designs the API?
It does not guess. The prompt gives every operation's path, or its reducer, mutation, or function name, and the store must expose it there.
Does a redirect to the sign-in page count as a refusal?
No. Only the listed refusal codes count. A redirect fails the check.

Other people's changes appear without a reload

If one customer buys the last unit, another customer looking at the same item should see it go out of stock. If staff work from an old view, they ship or restock the wrong things.

What StackBench does

  • One user changes something through the store's page in their own browser context, such as a purchase, a restock, a review, or a support reply.
  • A second user, in a separate browser context, already has the affected page open. From the moment the first user's action finishes, Playwright reads the text of the named element on the second user's page every 250 milliseconds, for up to 10 seconds, and never reloads it.

Passes when

  • The second user's page shows the change within 10 seconds.

Why it is a fair test

  • Any design passes if it updates the page in time, including re-fetching on a timer. No stack is required to push updates.
  • The user who made the change is never the one checked, so a page that only updates itself after its own writes does not pass.

What it does not prove

  • That data was stored correctly. These checks only test that open pages update; the restart and crash checks test the stored data.

Follow-ups

Why 10 seconds?
It is generous: pushed updates arrive in under a second, and a page that re-fetches every few seconds passes. In StackBench's October 21 review of check timing across saved runs, the stores that failed either never re-fetched or re-fetched every 20 seconds. 10 seconds is also the limit Jakob Nielsen gives for keeping a user's attention.
Don't Spacetime and Convex pass this for free?
They make it easier: their clients receive changes to the data they display automatically. That is a real difference between stacks, and StackBench measures stacks as an agent uses them. A store on any stack still fails if its page shows a copy it never refreshes.

Search order after purchases

The prompt says search results and filtered results are listed alphabetically, and the plain catalog is listed by purchase ranking, with ties broken by item name. On a new store nothing has been bought, so every item is tied and purchase ranking is the same as alphabetical order. A store that always sorts by purchase ranking looks correct until the first purchase, and then its search results come out in the wrong order.

What StackBench does

  • A customer buys Headphones by clicking its buy button in Playwright, and StackBench confirms in the stock table that its stock dropped by one. Headphones is now first in purchase ranking.
  • A second visitor reloads the catalog, sets the minimum-price filter to 1, which every item passes, and applies it. Playwright reads the item names inside search-results, in page order.
  • The visitor clears the filter and searches for the letter e, and Playwright reads the result names again.
  • The visitor clears the search, and Playwright reads the names in the plain catalog list.

Passes when

  • With the filter active and with the search active, the names are in exact alphabetical order.
  • With both cleared, Headphones comes first, followed by the rest in purchase ranking.

Why it is a fair test

  • Both ordering rules are in the prompt. The check only adds what the prompt leaves out: one purchase, so that the two orders differ and a store that ignores the rule can no longer pass by luck.
  • Every stack has the same seeded bug, a store that keeps purchase ranking while a search or filter is active, and the check must catch it on each.

What it does not prove

  • Ordering on later result pages, or with more than one purchase. The check reads the first page after a single purchase.

Follow-ups

Isn't this a feature check rather than a production check?
The ordering rules are features, and other checks test them on a new store. This check tests that they still hold once real purchases exist, which is the condition the prompt does not mention.

Customers buying at the same time

When several customers buy the last units at once, a careless store sells stock it does not have, loses one of the orders, or records the money twice.

What StackBench does

  • Six customers, each signed in in their own browser context, try to buy an item with three units left.
  • StackBench first builds all six purchase requests, each with its own customer's session, and then sends them together with one Promise.all of Node.js fetch calls from the controller container. A few checks instead click several browsers' buy buttons in parallel through Playwright.
  • It then reads stock from the stock table and orders from the order tables the prompt requires, and checks that every customer's reloaded page shows the same stock.

Passes when

  • Stock ends at exactly 0, exactly three customers have one order each, and revenue rises by exactly three sales.
  • Each request that did not buy was refused with HTTP 400, 409, or 422, or the stack's own error type. An error such as HTTP 500 fails.
  • If fewer than two of the requests were in flight at the same time, measured from when each was sent to when its reply arrived, nothing was contested, so the check is undecided.

Why it is a fair test

  • The check judges only the result, so each stack can use its own way of preventing overselling: a transaction, a lock, a Spacetime reducer, or a Convex mutation.

What it does not prove

  • Sustained load, or that the server ran the requests at the same instant. StackBench knows they overlapped on the way to the server, not inside it.

Follow-ups

Doesn't Spacetime pass this for free, since each reducer runs as one transaction?
Spacetime makes it easier, and so do Convex mutations. A store on those stacks still fails if its page computes the new stock and sends that number to the server instead of asking the server to subtract. On Spacetime that is the seeded bug these checks must catch.
Is this a load test?
No. It is a few customers contesting the same stock at once.

Changes made outside the store

A store's stock can change without going through the store, for example when a warehouse tool corrects the database. A store that keeps its own copy of stock, or only reacts to its own writes, then shows the wrong stock.

What StackBench does

  • The prompt requires the agent to keep stock in tables named item, warehouse, and stock (collections on MongoDB), and says direct updates to stock.quantity must change the stock the store uses.
  • StackBench changes one stock row directly:
    • PostgreSQL and Supabase: an UPDATE statement, run with psql through docker exec in the database container
    • MongoDB: updateOne, run with mongosh through docker exec in the database container
    • Spacetime: an UPDATE statement, run with the spacetime sql command through docker exec in the coding container, followed by a SELECT to confirm it
    • Convex: Convex's built-in patchDocumentsFields admin function, called with curl and the deployment's admin key
  • Live version: a customer's already-open page must show the new stock within 10 seconds, without a reload.
  • Alert version: a customer has asked on the item's page to be told when it returns. StackBench restores its stock directly, waits 75 seconds, and the customer signs in again in a new browser context.

Passes when

  • The open page shows the new stock within 10 seconds, or the customer sees the alert within 15 seconds of signing in.

Why it is a fair test

  • The prompt itself makes the stock table the source of truth for direct updates, on every stack.
  • The 75-second wait allows for a store that checks for restocks in a background job once a minute.

What it does not prove

  • That the store's other tables are correct. StackBench writes only the stock table and reads only the stock, order, and cart tables the prompt requires.

Follow-ups

Don't Spacetime and Convex pass this for free?
Their clients receive table changes automatically, so the live version is easier on them. The alert version is not: a store on any stack fails if it sends alerts only from inside its own restock code, which is how most failing Spacetime stores failed.
Do real Convex apps get writes like this?
Yes. Dashboard edits, npx convex import, and streaming import from Airbyte all change tables without the app's own functions. StackBench's write is a document edit with the admin key, the kind the dashboard makes.

A crash in the middle of checkout

If the database or the store's server dies while an order is being placed, a careless store can take the stock but lose the order, keep half an order, or lose orders it already confirmed.

What StackBench does

  • A customer has a two-item cart. StackBench reads and records the cart, stock, and orders from the database tables the prompt requires.
  • Before sending any request, StackBench starts a small shell script with docker exec inside the container it will crash. The script waits for one line of input, so the slow part, starting docker exec, happens before the crash and cannot shift its timing.
  • StackBench sends the customer's checkout request, immediately tells the script to crash, and sends 15 more copies of the same checkout request.
  • The script kills processes with SIGKILL, so nothing can save or clean up first:
    • Database trial: every process of the database
    • Server trial, on PostgreSQL and MongoDB: the script first sends SIGSTOP to every process of the agent's user in the coding container, confirms one of them is listening on the store's port, and then kills them all, so no part of the server can keep writing after another part dies
    • On Spacetime, Convex, and Supabase the store's code runs in the database, so the database trial covers both
  • StackBench then restarts what it killed:
    • Database trial: it restarts the database at once, on its existing data, while the checkout requests are still open, so the store's database driver can reconnect and finish them. The database must be ready within 30 seconds, and the unchanged store must answer within 10 seconds
    • Server trial: it waits until the database shows no client connections left, then runs start.sh again
  • It reads the orders, cart, and stock from the database again.

Passes when

  • The cart, stock, and orders are either exactly as before, or show exactly one complete order with the cart cleared and stock reduced.
  • Every checkout the store answered with success still exists, and earlier orders are unchanged.
  • If no request was in flight when the kill landed, judged from each request's send and reply times against the time of the kill, the trial measured nothing, so the check is undecided and its check file runs once more.

Why it is a fair test

  • The check judges only the recovered state, read straight from the database, so each stack can protect checkout its own way.
  • PostgreSQL and MongoDB get two trials because their store's code and data live in two processes that can fail separately. On the other stacks the store's writes run inside the database, so crashing the database covers them.

What it does not prove

  • Power loss, disk corruption, or every possible crash timing. Each process gets one trial with the crash right after the first request.

Follow-ups

Does this test that the database flushes to disk?
No. The machine keeps running, so data the database already handed to the operating system survives. Power loss is out of scope.

Scheduled work survives a restart and runs once

Stores schedule work, such as a restock due at 3 p.m. A store that keeps the schedule in a timer in memory loses it on a restart. A store that re-reads its schedule carelessly runs the same job twice.

What StackBench does

  • An admin schedules a restock of 5 units, due in 20 seconds, through the store's page in Playwright.
  • StackBench restarts the store while the restock is pending, the same way as the restart check: the store's server on PostgreSQL, MongoDB, and Supabase, the database process on Spacetime and Convex.
  • Once the restart is done, stock must rise by exactly 5 within 45 seconds. StackBench restarts the store again and checks that stock is still up by exactly 5, so the second restart did not replay the job.
  • A second check schedules a restock due in 120 seconds, restarts the store, and 30 seconds later confirms it has not run early and is still listed as pending. 130 seconds after the restock was scheduled, it must have run.
  • StackBench never moves a clock; every wait is real time.

Passes when

  • The restock runs exactly once, after its due time, across restarts.
  • If the restart took so long that more than 100 seconds had passed before the early check, it could no longer check for early running, so the result is undecided. This has never happened: across 368 saved runs of this check, the early check began at most 58 seconds after the restock was scheduled.

Why it is a fair test

  • The check judges only stock and the pending list, so each stack can schedule work its own way: a database table polled by a timer, a Spacetime scheduled reducer, or a Convex scheduled function.

What it does not prove

  • Tolerance to the server's clock being changed.

Follow-ups

Couldn't a store that restarts slowly escape a failure here?
Only by being more than 40 seconds slower than any store so far, and then the check file runs again before the run is excluded. A slow restart is undecided rather than failed because the machine, not the store, can be the slow part, and a failure would then blame a correct store.
Don't Spacetime and Convex pass this for free?
Both have schedulers that survive restarts, so it is easier on them. A store on those stacks still fails if it keeps its run queue in memory, and on Spacetime that is one of the seeded bugs these checks must catch.
Can customers schedule or cancel restocks by calling the server?
A separate check confirms they cannot: the admin's request succeeds, and the same request from a customer must be refused.

Lost replies and double submits

Sometimes an order reaches the server and is saved, but the connection drops before the reply gets back. The page does not know the order went through, so the store's code sends it again or the customer clicks again. A customer can also submit the same cart from two tabs at once. A careless store places two orders.

What StackBench does

  • A normal checkout must first produce one order, so the later results cannot come from a broken checkout.
  • StackBench then turns on a reply fault for that customer and clicks checkout. On HTTP stores, Playwright holds the checkout request, sends it to the server itself, records the answer, and then resets the browser's connection, so the reply never arrives. On WebSocket stores, every message the server sends back after the checkout is dropped.
  • StackBench waits until the database holds the new order and the fault has recorded a dropped reply.
  • The customer reloads, and StackBench sends a new checkout request for the same, already-ordered cart, as a customer clicking again would.
  • Separately, two tabs on the same account send checkout at the same moment.

Passes when

  • After the lost reply and the second request, exactly one order exists and stock dropped by one. After the two-tab checkout, again exactly one order.

Why it is a fair test

  • The fault only stops the reply. It never changes the request or the data, so the server saw a normal checkout and must recognize the repeat itself.

What it does not prove

  • Whether a stack's client library would resend the order on its own. StackBench sends the second request itself.

Follow-ups

Don't some stacks' client libraries prevent duplicates automatically?
StackBench does not rely on it. The second checkout is a new request for a cart that was already ordered, so only the store's server logic can refuse it.

Other customers' data never reaches the browser

A store can send a customer's browser other customers' data, such as every order in the database, and simply not display it. The page looks fine, but anyone can read the data in the browser's developer tools.

What StackBench does

  • Through the store's page, one customer saves a value with a code generated for that run, such as a shipping address.
  • Playwright records every HTTP response and WebSocket message each customer's browser receives, with the browser cache off so every response is fetched and recorded. Binary messages, including Spacetime's compressed ones, are decoded to text.
  • The owner's own recording must contain the value, which proves the recording captures that data.
  • A second customer then opens the same kinds of pages in their own browser context.

Passes when

  • The value never appears anywhere in the second customer's recorded traffic, even in data the page does not show.
  • If a response was still loading or could not be decoded, absence is not proven, so the check is undecided.

Why it is a fair test

  • Every stack's traffic is decoded to text and searched the same way, and the owner's positive result proves the decoding works on that stack.

What it does not prove

  • Every endpoint or encoding, or attacks that guess another customer's ids.

Follow-ups

How are Spacetime's binary WebSocket messages searched?
They are decompressed and decoded as UTF-8 before the search. The owner's own recording must contain the value, so a decoding gap would make the check undecided rather than pass.

Recovering from a dropped connection

Connections drop, on a train or when Wi-Fi changes. A careless store's page stays stale after the connection returns, or loses the customer's session.

What StackBench does

  • A customer who will lose the connection browses through a small forwarding proxy that StackBench starts with docker exec in the browser container. All of that customer's traffic goes through it.
  • To cut the connection, StackBench switches the browser context offline through Playwright and tells the proxy to refuse new connections and close every open one. It waits up to 5 seconds until every connection is confirmed closed and the browser reports that it is offline.
  • While the customer is offline, something changes: the same account adds an item from another browser context, or StackBench writes new stock to the database as in the outside-changes check.
  • A few seconds later StackBench reopens the proxy and switches the browser back online. The same page, never reloaded, must show the change.

Passes when

  • The page shows the change in time, 5 seconds for the cart and 20 seconds for stock, and the customer is still signed in with the full cart.
  • If the connections did not actually close, there was no outage, so the check is undecided.

Why it is a fair test

  • Switching the browser offline alone only pauses an open WebSocket and later delivers what it held. Closing the connections through the proxy makes every stack's client actually lose them.

What it does not prove

  • That data was stored correctly. This check only tests that the page catches up.

Follow-ups

What if a stack's client library reconnects on its own?
That makes this check easier on that stack, which is a real difference StackBench measures. The check only requires that the page ends up correct, however the store gets there.

04A run, start to finish

The agent builds the store in three levels, one agent session per level. The level of a feature comes from what it builds on:

  • L1: 4 features that build on nothing else: accounts, catalog items, staff access, and support intake
  • L2: 10 features that build on L1, such as the cart, purchasing and orders, and warehouse administration
  • L3: 13 features that build on L2, such as checkout, reviews, scheduled restocks, and stock alerts

Each level goes through these steps:

  1. Promptlists this level's features
  2. Agent buildsthe CLI runs until done
  3. Log auditchecks what the agent read
  4. Snapshotsaves the store's code
  5. Clean startrestarts from saved code
  6. Run checksempty database per file
  7. Unlockpassed features unlock dependents

Agent session

Each level starts with a prompt. The session ends when the agent's CLI exits after reporting that the store is running, or at 120 minutes.

  • The prompt text is the same on every stack except two parts: the stack setup section, with connection details and start instructions, and the stack-specific line in each feature's interface, such as an HTTP path on PostgreSQL or a reducer name on Spacetime. On Spacetime the setup also includes SDK skills, because stacks that are newer and less represented in model training get them.
  • The prompt asks for a production-quality application but does not list the production requirements the checks test, such as refusing other customers' requests, updating pages without a reload, or keeping an order intact through a crash.
  • StackBench starts the CLI inside the coding container with docker exec, in non-interactive mode. For Claude Code that means --print --bare --permission-mode acceptEdits: it never waits for a person, offers only the Bash, Edit, and Read tools, and approves its own file edits.
  • The prompt tells the agent to reply DEPLOY_COMPLETE, or UPGRADE_COMPLETE after the first level, when the store is running. StackBench also watches the CLI's log for that reply, in case the CLI does not exit after giving it.

Log audit

The checks are part of StackBench's source code, which is public on GitHub, and the agent can reach the web. An agent that read the checks could build to pass them, so after every session StackBench checks the agent's log for it automatically.

  • The log is the session record the CLI writes: every command the agent ran and every file it read with its tools. Reads done inside a script it wrote do not appear. StackBench lists every file the agent read outside /app and every URL or network address in its shell commands.
  • The run is thrown out as contaminated if the agent:
    • Read StackBench's checks, grading code, or prompt files
    • Connected to another run's ports
    • Fetched anything under tools/stack-bench in the SpacetimeDB repository, or its pull request, from GitHub or a mirror such as jsDelivr or Sourcegraph
  • A model that saw the checks in its training data is not detected.

Clean start

When a session ends, the running store may depend on things its code alone would not produce, such as a server the agent started by hand with different settings, or a package it installed by hand. Grading therefore never uses the running store. It rebuilds the store from the saved code.

  • StackBench saves a copy of /app with a SHA-256 fingerprint of every file. The copy leaves out what running the code produces:
    • Installed packages (node_modules)
    • Build output (dist, .vite)
    • Caches
    • Logs and pid files
  • It stops the store, deletes everything in /app except the agent's git history (.git), copies the saved code back, and runs the store's start.sh with no packages installed, so start.sh must install them itself.
  • After start.sh finishes, StackBench fingerprints every saved file again. If startup changed any of them, the store fails that level's grading, so the graded code is exactly the code the agent wrote.

Empty database for each check file

Checks are grouped into files by feature area. Data left by one file's checks could make the next file's checks pass or fail, so each file starts on an empty database. Checks within a file run in order on the same data.

  • Before each file, StackBench stops the store, empties the database, and starts the store again, which recreates the starting catalog and accounts the prompt supplies.
  • How the database is emptied, by stack:
    • PostgreSQL: dropdb --force, then createdb
    • MongoDB: db.dropDatabase(), run with mongosh
    • Spacetime: spacetime publish --delete-data
    • Convex: delete the backend's data folder and restart it
    • Supabase: run StackBench's reset function in Postgres, then delete the stored files
  • If a check file cannot be decided, for example because the browser crashed, StackBench empties the database and runs that file once more. If it still cannot be decided, the whole run is marked invalid.

Unlocking features

Features build on each other: checkout needs a cart, and a cart needs accounts. A feature passes only if every one of its checks passes. A feature that depends on a failed feature is marked blocked and does not pass.

  • The agent never sees check results or failure messages, and a failed feature stays failed. It can only notice which features the next level's prompt asks for.

Score

Score is the percentage of features that pass every check, averaged over runs. Invalid runs are left out.

  • A run's score is the number of its features marked passed when its last level has been graded, out of all the features in the run.

06Time, rate limits, and cost

Time limits

  • An agent session stops at 120 minutes. A whole run has 240 minutes of working time, not counting time paused for rate limits or spent waiting to be graded, since only a limited number of runs are graded at once.
  • A run is marked invalid and left out of scores when:
    • It runs out of time
    • It hits the spending cap
    • A check file could not be decided twice
    • The log audit finds contamination
    • A container, the browser, or the provider's API fails
  • Reruns follow rules fixed before any run starts:
    • The study's plan lists which invalid outcomes are rerun and how many times, and applies that to every run alike
    • An operator can also exclude a specific run, and the stated reason is published with the results

Rate limits

  • When the provider refuses a request for rate limiting (HTTP 429 or 529), StackBench:
    • Pauses the session for 1 minute, then 2, then 5, resuming it after each wait
    • If it is still rate-limited, the next wait of 10 minutes would take the total past 15 minutes, so the run pauses until an operator resumes it by hand

Cost

  • Cost is model usage priced at each model's public API rates, from the token counts the provider reports, averaged over the same runs as the score. For runs on a subscription plan, it is what the same usage would cost through the API.
  • If a reply reports no usage, for example because the connection broke, the request is counted at its reserved maximum, and the run's cost becomes an upper bound.

07Hard questions

How is this set up?
Everything is a Docker container on one machine.
  • The controller runs StackBench, on the host's network, with control of Docker so it can start the other containers
  • Each run gets four containers, or ten on Supabase: the database, the agent's coding container, a broker that holds the model provider's API key, and Chromium
  • The run's containers share one private network behind a firewall that blocks the host, the controller, and other runs
  • The controller drives Chromium with Playwright through docker exec

Follow-ups

Can runs interfere with each other?
They cannot reach each other. They share the machine and one read-only package mirror:
  • Each run has its own network, and the firewall rejects other runs' addresses
  • Runs share the host's CPUs and the package cache
  • Every container has fixed limits: the coding container 2 CPUs, 4 GB, and 2,048 processes; the database 1 CPU, 2 GB, and 256 processes; the browser 1 CPU, 4 GB, and 512 processes; the broker 256 MB and 32 processes
  • The package mirror allows no publishing, unpublishing, or sign-ups, so no run can place a package another run installs
Giving the controller the Docker socket is full control of the machine. Is that safe?
Nothing in a run can open a network connection to it: the controller sits on the host's network, and every run's firewall rejects the host's addresses. The controller still reads files the agent wrote, such as the store code and the CLI's log, and treats them only as data.
How is it graded automatically?
After each session, StackBench:
  • Stops the store, restores the saved code into /app, and starts it with start.sh as a first start
  • Before each check file, empties the database and restarts the store
  • Runs each check's steps: page steps with Playwright in Chromium, server requests with Node.js fetch, and database steps with docker exec
  • Passes a feature only if all its checks pass, and scores the run as the percentage of features that pass

Follow-ups

Does a person or an AI judge any of it?
No. Every check is a scripted list of steps with a fixed expected result, and the same checks run on every stack. Only the stack-specific commands differ, such as which database tool writes stock.
What if the store is just slow?
Each step waits for the page: 5 seconds unless the check sets a longer window, such as 10 seconds for live updates. A store slower than that fails the step.
How can checks find elements in a store each agent designed?
The prompt lists a name for each element the checks use, and the agent puts that name on the element as its id or data-role. Nothing else about the page is fixed.

Follow-ups

What if the agent leaves a name off?
The check cannot find that element, so it fails. The names are part of the prompt, so leaving one off is a store failure.
Can the agent see or game the checks?
Reading them in the open is caught. Hidden reads, training data, and guessing are not:
  • The checks run in the controller, which nothing in a run can reach
  • The checks are public in the SpacetimeDB repository, and the agent can reach the web. Any read or download of StackBench's files in the agent's log voids the run
  • Test account names change every run, so a store cannot recognize test accounts by name
  • A model that saw the checks in its training data is not detected
  • An agent that guesses what production checks test can build for them. That is the behavior StackBench measures

Follow-ups

Could an agent fetch the checks and hide it?
A deliberate one could. The audit is built to catch accidental and naive reads:
  • The audit pattern-matches the URLs and file paths in the agent's shell commands, so an encoded URL, or a fetch inside a script the agent wrote, would not match
  • The agent can also write to the folder that holds its own log, because the CLI writes the log as the agent's user
  • Stopping a model that sets out to cheat would take keeping the checks private, or blocking those GitHub paths at the network level, which HTTPS does not allow without intercepting traffic
Has any agent tried?
Nothing in the saved runs suggests it:
  • Across the logs of 937 saved runs in StackBench's results, 17,378 files including resumed sessions and tool output, none contains the text tools/stack-bench
  • In 13 runs the agent read its own log, to re-read the prompt or earlier output after its context filled up. No log shows a command that edited or deleted a log
Can the agent test its own work?
Yes. The coding container has Chromium and Puppeteer Core, a Node.js library for controlling it, and the prompt says where they are.
Could something the agent left running fake a pass?
No.
  • Grading stops the store, deletes /app except .git, restores the saved code, and starts the store from scratch
  • Grading fails if startup changes any saved file
  • Each check file starts on an empty database
How do you know a failure is the store's fault?
Every check is tested on every stack before results are published:
  • It passes on that stack's correct reference store
  • It fails when a bug it targets is planted in that store
  • It fails on an empty site
  • It reads only the element names, server operations, and stock, order, and cart tables the prompt lists, so every other design choice is the agent's

Follow-ups

What about flaky checks?
Two protections, and one limit:
  • A check StackBench cannot decide, for example after a browser crash, is retried once and never scored as a store failure
  • Each check must pass on every stack's reference store and fail on the empty site before results are published
  • Each control runs once per stack, so a check that passes a control by luck is not caught by repeating it
What counts as a measurement problem?
A check result StackBench could not decide: its own tooling failed, such as a browser crash, or the moment the check had to observe had passed, such as when a restart took so long that a scheduled job's due time arrived first. That check file runs once more, and if it is still undecided, the run is marked invalid and left out of scores.
Why are the production checks left out of the prompt?
People who ask an agent for an app describe its features and expect it to work properly, without listing every edge case. The prompt asks for a production-quality application, and StackBench measures how well agents deliver production-quality features by default.

Follow-ups

Isn't that a trick question for the agent?
The prompt tells the agent the store must be production quality. The production checks test what that means for each feature, such as refusing another customer's request or keeping an order intact through a crash.
Why does one failed check block later features?
Later features depend on earlier ones working. If the cart fails a check, checkout's results would measure the cart's bug, so the features built on the cart are marked blocked.

Follow-ups

Doesn't one early failure then cost many features?
Yes, by design. A cart that fails any of its checks blocks checkout, even if checkout itself would work. StackBench treats a feature built on a failed one as not delivered.
Does Spacetime get more help than the other stacks?
Yes, on purpose. Stacks that are newer and less represented in model training get SDK skills in their stack setup, and today that is Spacetime:
  • Every stack gets a setup document of about 130 to 280 words with its connection details and start instructions
  • Spacetime's setup also includes three of SpacetimeDB's public SDK skills (TypeScript server, TypeScript client, and CLI), the same files Spacetime publishes for developers' agents
  • It also includes a StackBench note on running spacetime dev inside the container
  • The features, the checks, and the grading are the same on every stack

Follow-ups

Why not give every stack its skills?
StackBench's rule gives SDK skills to stacks that are newer and less represented in model training, and today only Spacetime meets it. The other stacks get their setup document.
Do the skills tell the agent what the checks test?
No. They are general SDK reference material. StackBench's authoring rules forbid putting test probes or check details in any stack's guidance, and the skill text is kept with every run's evidence.
How much do the skills help?
StackBench has a study setting with no Spacetime skills, so their effect can be measured as a separate experiment.
Who decides which stacks get skills?
It is set per stack in the study's settings file, which is fixed before any run and recorded with the results.
Is writing straight to the database fair to every stack?
Every stack's prompt requires the same item, warehouse, and stock tables, and every stack's reference store passes these checks.

Follow-ups

Do real Convex apps ever get data written from outside their own functions?
Yes. Convex supports it in several ways:
  • Editing documents in the Convex dashboard
  • npx convex import, which loads CSV or JSON into a table
  • Streaming import, which lets Airbyte write records from another system into Convex tables (in beta)
  • StackBench uses patchDocumentsFields, a built-in Convex system function for editing documents, which requires the deployment's admin key

Sources: Convex streaming import, Convex import and export, Convex dashboard data editing, Convex system function patchDocumentsFields

Does a Convex store even notice such a write?
Yes, if it reads stock from the table. Convex reruns every query that read the changed data, whatever made the change, and pushes the new result to open pages. A store fails only if it keeps its own copy of the stock, or sends alerts only from inside its own restock function.

Sources: Convex dashboard data editing

What is this check really testing?
That the stock table is the store's single source of truth, as the prompt requires. A warehouse correction made outside the store must update stock everywhere and trigger the alerts it should.
Do the live-update checks favor real-time databases?
No stack is required to push updates:
  • A live-update check has one user change something, such as staff replying to a support case, and expects another user's open page to show it without a reload
  • A store that re-fetches data on a timer passes, as long as the page updates within 10 seconds
  • Every stack's reference store passes every live-update check

Follow-ups

Why 10 seconds?
Because past about 10 seconds a page no longer feels live:
  • 10 seconds is the longest of Jakob Nielsen's three response-time limits: the point where a user's attention leaves the task
  • A page that updates within 10 seconds still updates while the user is looking at it, and a slower one is effectively a page the user must reload
  • The window is generous for every design: pushed updates arrive in well under a second, and a store that re-fetches every few seconds passes
  • The stores that fail re-fetch every 20 seconds or more, or never re-fetch at all

Sources: Nielsen Norman Group, response time limits

Why do stock alerts get a 75-second wait when live updates get 10 seconds?
An alert can come from a background job, so its window leaves room for a job that runs once a minute: 75 seconds, then 15 seconds to show. A live update is about an open page reflecting a change, so it gets the 10-second window.
What happens when a run hits a time limit or the spending cap?
The run is marked invalid and left out of scores. The study's plan, fixed before any run starts, decides whether it is rerun.

Follow-ups

Doesn't leaving those out favor slow or expensive models?
Those runs are left out rather than scored as zero, and the same rule applies to every model. How many runs each model loses to limits is part of the study's evidence.
Clockwork Labs makes Spacetime. Why trust the results?
StackBench is developed by Clockwork Labs, Convex, and Emergent. Spacetime (Clockwork Labs) and Convex are both included on the leaderboard.
  • Every stack gets the same feature list and the same checks
  • Each stack's checks are proven on that stack's own reference store before its results are published
  • Every claim about how StackBench works links to the code that implements it
Did every model get the same prompt?
At the first level, yes: every model on a stack gets exactly the same prompt, and across stacks only the stack-specific parts differ. Later levels list only the features that run has unlocked, so two runs that passed different features get different later prompts.
Can we read the code?
Yes. Each green code label on this page opens the cited lines and links to them in the SpacetimeDB repository on GitHub.

async function setOffline({ input, capabilities, signal }: ActionArguments<OfflineInput>) {
  const actor = actorFor(capabilities, input.actor);
  const browser = capabilities['browser-interaction'];
  const offline = input.offline !== false;
  // Emulation alone pauses an open WebSocket and later delivers what it held.
  if (!actor.networkInterruption) {
    inconclusive('network-not-interrupted', { actor: input.actor,
      detail: 'this client was not opened with an interruptible network' });
  }
  let connections: { closed: number; open: string[] } | undefined;
  const urlBefore = actor.page.url();
  if (offline) {
    // The device goes offline first, as a real outage reports; then its connections are cut.
    await actor.page.context().setOffline(true);
    connections = await actor.networkInterruption.interrupt();
    if (connections.open.length) {
      inconclusive('network-not-interrupted', { actor: input.actor,
        detail: `still open after the interruption: ${connections.open.slice(0, 3).join('; ')}` });
    }
  } else {
    // Reopen forwarding while emulation still blocks the page, then restore the page's network.
    await actor.networkInterruption.restore();
    await actor.page.context().setOffline(false);
  }
  await browser.sleep(input.settleMs ?? 500, signal);
  const browserOnline = await actor.page.evaluate(() => navigator.onLine);
  if (browserOnline === offline) {
    // An application that reloads itself while offline lands on the browser's error
    // page, which ignores offline emulation and does not recover when back online.
    if (offline && !urlBefore.startsWith('chrome-error://')
      && actor.page.url().startsWith('chrome-error://')) {
      fail('page-error', { detail: 'the application reloaded while offline and left the browser error page' });
    }
    throw new Error(`setOffline requested browser network ${offline ? 'offline' : 'online'}, `
      + `but navigator.onLine remained ${browserOnline}`);
  }
  return { offline, browserOnline, ...connections };
}
