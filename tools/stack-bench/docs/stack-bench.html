Technical reference

StackBench

StackBench measures how well agents deliver production-quality features by default. Each agent builds an online store from a feature list on one stack, and StackBench scores how many of its features hold up under production conditions.

Technical reference for the ecommerce track through depth 3, October 2026. StackBench is developed by Clockwork Labs, Convex, and Emergent. Spacetime (Clockwork Labs) and Convex are both included on the leaderboard.

Score is the percentage of features that pass every check, averaged over runs. Production conditions include many users at once, live updates, restarts, dropped connections, writes from outside the store, and permissions. The prompt includes the feature list and a request for an app suitable for real users, and the production conditions are not in it.

Each check is proven on every stack in three ways: the stack's reference app must pass it, seeded bugs in that reference app must make it fail, and an empty app must fail it.

How a run works

PromptFeature list, starting catalog, stack setup, and interface IDs.
BuildThe agent writes the store code in a sandbox, one session for each depth.
GradeStackBench runs every check for the features built so far.
ScoreA feature passes only when every one of its checks passes.

A run is one model building the store once on one stack. Features form a dependency graph: checkout depends on the cart, and the cart depends on accounts and the catalog. StackBench tasks the agent with the root features first, grades them, and then starts a new session in upgrade mode with only the features whose dependencies all passed. A failed feature blocks every feature that depends on it, and the run ends when no new feature unlocks.

The 1.1 runs include no repair sessions, in which an agent would see failed checks and fix them, so the agent never sees a check result.

The prompt

StackBench assembles one prompt per session. In order it contains:

  1. The opening line, which says to build the store and leave it running or, at later depths, to add the listed features and keep the existing ones working.
  2. A request for an app suitable for real users.
  3. The run rules: work in /app, listen on 0.0.0.0, provide start.sh, seed an empty database, and keep an existing one.
  4. The stack setup with connection details and start rules. For Spacetime it also includes the SDK skills for the TypeScript server, the TypeScript client, and the CLI.
  5. The feature list for this session, one short paragraph per feature.
  6. The starting catalog of items and warehouses, as JSON.
  7. The application interface: the IDs of buttons, fields, and values StackBench reads, the server actions it calls directly, and the stock tables it writes.

The production conditions are not in the prompt. The definition files call this the expected treatment: scored but not stated. Experiments can also use requested (stated and scored) or observed (neither), but the dependency progression always uses expected, and study conditions cannot override it.

The run rules and the application interface are the parts of the prompt written for StackBench. StackBench uses the interface names to find a button, a number, or a server action, and every design choice stays with the agent. When an interface rule is unclear and an agent misreads it, StackBench widens the check to accept the reading.

The build

Agents

The 1.1 runs used four agent CLIs, each pinned to one version in the sandbox image: Claude Code, Codex, Grok Build, and Antigravity. Web search and subagents were off for every 1.1 run. The study plan sets the reasoning effort for each model.

Sandbox

  • The sandbox is read-only, drops all Linux capabilities, blocks privilege escalation, and runs as an unprivileged user. The agent can write only /app and its transcript folder.
  • The sandbox holds no StackBench source, checks, grader, Docker socket, or provider key. Provider keys stay in a separate broker, and the agent receives a short-lived token.
  • Each run has its own network. It allows loopback, the shared npm cache, and public web traffic on ports 80 and 443, and blocks the host, private ranges, other runs, and IPv6. Fetching StackBench's own source counts as contamination and invalidates the run.
  • The sandbox has 2 CPUs and 4 GiB, and each grading browser has 1 CPU and 4 GiB.

Time and spending

A coding session can last up to 120 minutes and a whole run up to 240 minutes. The run limit excludes planned pauses and waits for a grading slot. A spending cap per run guards against runaway model usage, and the broker refuses any request whose worst-case cost would exceed it. The cap value is not part of the results, and a run that reaches it is invalid and rerun.

Upgrade sessions

Each depth is a new agent session on the existing store code and data, and the earlier interface rules stay in the prompt. Every grade starts the store from its saved store code, so a store that relies on state left over from the build fails the checks that reach that state.

Grading

StackBench clicks through the store in a browser and checks that the database matches what the page shows. The browsers are Chromium, driven through Playwright.

Outcomes

Each check ends as passed, failed, blocked (its feature never unlocked), inconclusive (StackBench could not take a valid measurement, for example when a server action never accepted a valid call, so a refusal cannot be told apart from a missing route), or harness failure (StackBench itself failed). Failed and blocked checks count against the store and score zero. An inconclusive check or a harness failure invalidates the run, as do reaching the time limit or the spending cap, losing the model provider, and contamination. Study design describes how invalid runs are handled.

The checks

A check is a scripted sequence of browser actions, direct calls, and database reads with one pass condition. Each check is written once and runs on all five stacks.

Each production check states its claim in one sentence in the definition files, for example "Stock alerts are private to the requesting customer." A reviewer can judge from that sentence whether a store in production needs the behavior.

How the checks are proven

Reference apps

Each stack has a reference app, a store written for that stack by the StackBench developers, and it must pass every scored check. The Spacetime, PostgreSQL, and MongoDB reference apps cover depths 1 to 6, and the Convex and Supabase reference apps cover depths 1 to 3.

Seeded bugs

For each check, StackBench keeps small edits to the reference app that introduce the bug the check exists to catch, such as a missing row lock or an alert sent only from the restock code. A seeded bug counts as caught only when its target checks fail at an assertion, no other check fails, and nothing is inconclusive. Every one of the 113 checks has seeded bugs on every stack.

Empty app

An empty store must fail every scored check conclusively, which rules out checks that pass without the feature.

Qualification

A calibration file pins the recipe hashes, which cover the feature list and checks, the hashes of the starting data, the five reference apps, and the five seeded-bug sets, and the exact list of scored checks. Qualification means the reference apps pass, every seeded bug is caught, and the empty app fails, all on that pinned definition. A change to any pinned input makes the evidence stale.

Status: the current definition (113 checks, 177 points) is not yet formally qualified. A full depth 3 reference grade on 16 October passed all 177 points on every stack, and after each later check change the reference apps passed the changed checks and every seeded bug for them was caught. Formal qualification is the next planned step.

Time budgets

Each group of checks has a runtime budget of twice the slowest reference measurement, rounded up, and never less than the waits the checks declare. A reference app that runs over budget fails qualification. A model's store that runs over keeps its result, and the overrun is recorded.

Audits of saved stores

Every saved run keeps its store code, so a grading change can be replayed on earlier stores without new model calls. StackBench also audits checks against saved stores. Reviewers read failing and perfect-scoring stores to find false failures, where a reasonable design fails a check, and false passes, where a bug slips past every check. Recent examples are under Fairness rules.

Reruns and invalidation

When StackBench fails on its own side (grader, harness, credentials, or infrastructure), the failure is recorded, the cause is fixed, and the affected runs are rerun. If a fix would change how earlier runs score, those runs are regraded from their saved store code or rerun. A failure caused by the store stays in the results.

Fairness rules

A production check is judged on need and measurement

A check is unfair only if a store in production would not need the behavior, or if StackBench measures it wrongly. Production conditions are left out of the prompt by design, so their absence from the prompt is never a reason to drop a check.

Checks accept every reasonable design

If a store built on a reasonable reading of the feature list fails a check, the check is changed to accept that design. The interface rules are never tightened to make grading easier.

Timing that the prompt leaves open allows reasonable designs

Where the prompt states no latency, a check waits long enough for a reasonable design. A back-in-stock alert has 75 seconds after stock returns plus 15 seconds on a fresh sign-in, so a sweep that runs once a minute passes. Live updates are the exception: the StackBench owners decided that a live update must appear within 10 seconds.

Every check must pass before dependents unlock

Production checks gate progression exactly as feature checks do.

The prompt holds only what the agent needs

When an agent trips on a StackBench problem, such as a wrong signal from the harness, the harness is fixed. No sentence is added to the prompt to work around it.

Adding a stack leaves other stacks' results unchanged

Stack behavior lives in per-stack adapters, and each stack's qualification scope hashes only that stack's adapter files and interface rules, so adding a stack leaves the other stacks' evidence valid.

Recent audit outcomes

  • New check, timing corrected. A new check tests that stock written outside the store still triggers a requested stock alert. Two Convex stores swept pending alerts once a minute and failed only because the check waited about 20 seconds. The window was widened and both stores now pass. The other 18 failing stores send alerts only from their own restock code.
  • Live support updates confirmed. 43 runs failed the live support-case check. Of those stores, 40 never refresh the customer's support page and 2 poll it every 20 seconds. The remaining Convex run failed once in grading and passed three replays. No fault was found, and its recorded result was left as graded.
  • Check claim narrowed. Staff stock editing was reported as a false pass of the staff restock check. The feature list includes staff and inventory roles, so a staff stock editor is a reasonable design, and the check's claim was narrowed to what it tests.
  • Timing aligned. The other alert checks, the buy-now live check, and the last-unit check were brought in line with the timing rule. None of the 135 counted runs had failed them on timing alone, so no counted score changed.

Cost

Cost is the average spend on model usage per run. The broker meters every model request and prices it at the provider's API list rates from the token counts the provider reports. A run's cost is exact when every request was priced from reported usage, an upper bound when some request had to be charged at its maximum, and unknown when some request could not be priced. Runs on subscription accounts are priced the same way.

Study design

  • Each model runs three times on each stack from the same feature list.
  • Runs execute in parallel on one host in a seeded, rotated order, so no stack always starts first.
  • Each run uses one credential for its whole duration.
  • Model requests that hit a rate limit or a provider error are retried with backoff, and a longer outage holds the run until an operator resumes it.
  • Invalid runs are excluded, recorded with their reason, and replaced by a rerun.
  • Each completed study is archived with a checksum manifest and recorded in a ledger, and each regrade is archived with the run it corrects.

Limitations

  • Results describe each stack with its stack setup. Spacetime runs from this repository's branch, which carries SDK fixes, and its stack setup includes SDK skills. The other stacks receive connection details and start rules without skills.
  • Gating amplifies single failures. One failed check early in the graph can cut a run's score sharply, so scores depend on which checks sit early in the graph.
  • Scores depend on how the feature list is divided. How work is split into features, checks, and points changes the percentages. Results compare only within one version.
  • One product. Every result comes from one online store, and other kinds of apps may rank stacks differently.
  • Small samples. Each model runs three times on a stack. Agent output varies between runs and cannot be reproduced exactly.
  • Shared blind spots. The same people write the checks, the reference apps, and the seeded bugs, so a misunderstood requirement can be built into all three. Audits of saved stores are the guard against that.
  • Untested areas. StackBench restarts and kills processes, but it does not test power-loss recovery, full serializability, throughput, or every endpoint for privacy.
  • Host effects. Runs share one machine, and host load and the npm registry at build time can affect a run. Rotated ordering spreads load across stacks.

FAQ

Clockwork Labs makes Spacetime. Why trust the results?

StackBench is developed by Clockwork Labs, Convex, and Emergent. Spacetime (Clockwork Labs) and Convex are both included on the leaderboard. Each check is written once for all stacks, each has a reference app and seeded bugs on every stack, and checks are audited against saved stores. Audit corrections apply to every stack, and after the October alert timing fix two Convex runs gained a point.

Why are the production conditions missing from the prompt?

StackBench measures whether agents meet production conditions without being told them. The prompt includes a request for an app suitable for real users, and the checks test concurrency, permissions, live updates, and restarts.

Is it unfair to grade conditions the prompt does not state?

A check is unfair only if a store in production would not need the behavior, or if StackBench measures it wrongly. Each production check states its claim in one sentence so a reviewer can judge whether a store needs it, and audits of failing stores test whether StackBench measures it correctly. A missing statement in the prompt is never a reason to drop a check.

Does the live-update requirement favor real-time databases?

In a store used by many people at once, open pages must show current stock, orders, and support status. The PostgreSQL and MongoDB reference apps pass every live check using sockets, and the Supabase reference app passes them using Realtime. Of the 43 stores that failed the live support-case check, 40 never refresh that page, and many of them poll the signed-in account's role every few seconds.

Why does one failure block so much of the score?

Features build on each other, and a checkout built on a cart that loses writes inherits the bug. Gating counts a feature only when everything it depends on passes.

How do you know a failing check is the store's fault?

Qualification requires each check to pass on that stack's reference app, catch its seeded bugs, and fail on the empty app, and the last full reference grade, on 16 October, passed every check on every stack. When StackBench cannot measure a check, the check is inconclusive, or a harness failure if StackBench itself broke, and the run is invalidated instead of scored. Disputed checks are settled by reading the failing store code.

How are timing windows chosen?

Where the prompt states a time, such as a reservation that holds stock for 90 seconds, the check allows that time plus slack. Where the prompt states no time, the window must fit a reasonable design, and a stock alert has 75 seconds plus 15 on a fresh sign-in. Live checks allow 10 seconds.

Spacetime's stack setup includes SDK skills. Is that an advantage?

It may be, and the Limitations section records it. The skills are API reference for the Spacetime SDK. The other stacks receive connection details and start rules without skills.

Can an agent see the checks or the grader?

No. The sandbox holds the store code, the prompt, and web access for packages and documentation. Checks, reference apps, and StackBench source are outside it, and fetching StackBench source from the web invalidates the run.

Are three runs per model on a stack enough?

Three runs show large differences between stacks. Runs of one model can differ widely: GPT-6.1 Sol's three Spacetime runs scored 113, 176, and 177 points. A ranking of models a few points apart is not supported.

What does the score mean?

The percentage of the 27 features at depths 1 to 3 that pass every check, averaged over a model's runs on a stack. A blocked feature counts as failing.

Is cost comparable between models?

Each run's model usage is priced at its provider's API list rates from reported token counts, so costs compare what the runs would cost through each API. Upper-bound and unknown costs are marked as such.

What happens when StackBench itself breaks?

The run is invalid, excluded, recorded with its reason, and rerun after the fix. If the fix would change how earlier runs score, they are regraded from saved store code or rerun.

Glossary

agent
The coding CLI that builds the store, driven by a model (Claude Code, Codex, Grok Build, Antigravity).
model
What the leaderboard ranks, run through one agent at one effort setting.
stack
The database or backend the store is built on.
store
What the agent builds: an online store with accounts, catalog, cart, checkout, staff tools, and support.
store code
The code the agent produces, saved at each depth.
run
One model building the store once on one stack. Internally an attempt, and each process that executes it an execution.
prompt
Everything the agent receives in a session.
feature list
The features inside the prompt, one short paragraph each.
stack setup
The per-stack part of the prompt: connection details, start rules, and for Spacetime its SDK skills.
application interface
The IDs, server actions, and stock tables StackBench uses. Internally contracts or hooks.
feature
A node of the dependency graph, which passes when all its checks pass.
depth
A feature's position in the graph: root features are depth 1, and a feature is one deeper than its deepest dependency. The definition files label depths L1 to L6.
check
One scored sequence of steps with a pass condition. Its ID joins the pack ID, the check group, and the criterion, for example ecommerce.spec.live-state + managed-support + 613a.
production check
A check for behavior the feature list does not spell out. Internally a guarantee role or production category.
treatment
Whether a production condition is stated and scored: expected (scored, not stated), requested (both), or observed (neither).
gating
The rule that a feature unlocks its dependents only when all its checks pass.
reference app
A store written by hand for one stack that must pass every check.
seeded bug
A small edit to a reference app that one or more checks must catch. Internally a mutation.
empty app
A store with nothing in it, which must fail every scored check conclusively. Internally the null control.
calibration
The file that pins a definition's hashes and check list for qualification.
qualification
Reference app, seeded-bug, and empty-app evidence on one exact pinned definition.
pack
A module of the definition that holds a feature or production family: its prompt text, interface rules, checks, and time budget.
recipe
The selection of packs, starting data, and framing that yields one prompt and one set of checks.
version
A numbered release of the feature list and checks, such as StackBench 1.1.
server action
Internally a named action. A server operation StackBench calls directly, declared once and called through each stack's interface: an HTTP route, a reducer, a Convex mutation, or a Supabase RPC function.
regrade
Running current checks on saved store code without model calls. A regrade can correct a recorded score but never counts as an extra run.
invalid run
A run excluded because its measurement is missing or compromised: a harness failure, inconclusive grade, timeout, spending cap, provider loss, or contamination.
sandbox
The isolated container where the agent works.
broker
The container that holds provider keys, meters model requests, and enforces the spending cap.
appliance
The Docker deployment that runs studies on one Linux host.
campaign
A frozen study plan and its results.
