Technical reference

StackBench

Each agent builds an online store from a feature list on one stack, and StackBench scores how many of its features hold up under production conditions.

01How it is set up

HostOne Linux machine running Docker Engine. Every part of StackBench is a Docker container on it.
ControllerStackBench itself, which starts every other container on the host's Docker Engine.
  • TypeScript on Node.js
  • Image built on Microsoft's Playwright image (Ubuntu 24.04)
  • Started by Docker Compose with network_mode: host
  • Host's /var/run/docker.sock mounted, so it can run docker create, docker exec, and docker rm
Each runThe controller creates a Docker bridge network and starts the database container on it. Every other container of the run starts with --network container:<database container>, so all of them share one network namespace and reach each other on localhost.
Coding containernode:22-slim (Debian) with:
  • git
  • Chromium
  • Puppeteer Core: Google's Node.js library for controlling Chromium, used only by the agent to test its own store
  • Claude Code 2.1.284
  • Codex 0.159.3
  • Grok CLI 1.0.46
  • Antigravity 1.3.2
DatabasesEvery image is pinned by its sha256 digest.
  • PostgreSQL: postgres:16
  • MongoDB: mongo:7
  • Convex: Convex's self-hosted convex-backend image
  • Supabase: seven containers (Postgres, GoTrue, PostgREST, Realtime, Storage, Edge Runtime, and an Envoy gateway)
  • Spacetime: spacetimedb-standalone, compiled with cargo from this repository at the release commit
FirewallOne nftables table in the shared namespace, loaded by a one-off docker run --network container:<database> --cap-add NET_ADMIN --entrypoint nft. Outgoing traffic is dropped unless allowed.
  • Allowed: loopback
  • Allowed: replies on open connections
  • Allowed: the package cache on port 4873
  • Allowed: TCP 80 and 443 to public IPv4 addresses
  • Rejected: the host's addresses
  • Rejected: every private and reserved IPv4 range
  • Rejected: everything else, including IPv6
BrokerA Node.js HTTP server in its own container in the shared namespace that holds the model provider's API key and enforces the spending cap.
BrowserA container running Chromium in the shared namespace, with a read-only filesystem and 512 MB of tmpfs. Playwright 1.62.1 in the controller starts Chromium here with docker exec -i and sends Chrome DevTools Protocol messages over that exec's stdin and stdout.
Package cacheverdaccio/verdaccio:6, a private npm registry that proxies the public one and keeps every package it downloads. The controller attaches it to each run's network, so coding containers install through it.

Controller

  • The controller runs on the host's network, outside the run's namespace. The firewall rejects the host's addresses, so nothing in a run can open a connection to the controller, the checks, or the model provider API keys.

Coding container

  • Container flags:
    • --read-only
    • --cap-drop ALL, then CHOWN, DAC_OVERRIDE, FOWNER, KILL, SETGID, and SETUID added back
    • no-new-privileges
    • CPU, memory, and process limits
  • Writable paths:
    • /app: the store code, bind-mounted from the controller's work folder
    • /tmp and the agent's home: tmpfs
    • The CLI's log folder
    • On Spacetime, the SDK and CLI are mounted read-only
  • Web search is off and sub-agents are refused for every agent. Claude Code runs with --bare, which offers only Bash, Edit, and Read.
  • Chromium and Puppeteer Core, a Node.js library for controlling Chromium, are installed so the agent can test its own store, and the prompt says where. Grading uses Playwright from the controller instead.

Broker

The broker holds the API key for the agent's model calls, such as an Anthropic or OpenAI key, or the login token of a subscription plan such as Claude or ChatGPT. The agent's CLI gets only the broker's localhost URL as its API address and a random session token.

  • The broker refuses any request without the session token.
  • For every other request it removes the auth headers the CLI sent, adds the provider's API key, and forwards it over HTTPS to the provider:
    • Anthropic: api.anthropic.com
    • OpenAI: api.openai.com, or chatgpt.com for a ChatGPT subscription
    • xAI: api.x.ai, or Grok's CLI proxy for a subscription
    • Google: the Gemini API, or Antigravity's host for a subscription
    • OpenRouter: openrouter.ai
  • For each request, the broker:
    • Reserves its maximum cost: the request's size in bytes counted as input tokens, plus its maximum output tokens, at the model's rates
    • Answers HTTP 402 and forwards nothing if spent plus reserved plus that maximum would pass the cap

02How the store is tested

Playwright

Playwright is a Node.js library that controls a browser from code: open a URL, click an element, type into a field, read text. StackBench's checks run as Playwright steps.

  • Chromium opens no debugging port, so its only control channel is the docker exec pipe from the controller and nothing on the run's network can drive it.
  • Each simulated customer is a separate Playwright browser context, with its own cookies, local storage, and video recording.
  • Usernames in checks are written as {user:name} and get the run's unique suffix, so no account name repeats across runs.

How checks find things

The prompt lists the interface names StackBench reads, such as notifications-toggle or stock-alert-delivery. The agent puts id on one-off elements and data-role on repeated ones.

  • A name becomes the CSS selector [data-role="name"],#name. Layout, data model, libraries, and transport are the agent's choice.

Example check: back-in-stock alert

  1. Stock to 0written to the database
  2. Request alertas the customer
  3. Stock to 1written to the database
  4. Wait 75 s
  5. Sign in freshnew browser
  6. Expect alertwithin 15 s
  • Checks are JSON files. Each step names an action, such as dbSetStock, wait, click, or expect, which StackBench looks up in its action registry and runs with a time limit.
  • expect with within: 15000 polls the page for up to 15 seconds. The 75-second wait before it leaves room for a store that checks stock once a minute.

Direct server requests

Some checks send a request to the store's server without the page, to test rules a page could hide, such as whether one customer can cancel another's order.

  • The prompt has the agent expose each named operation in its stack's own form:
    • PostgreSQL and MongoDB: an HTTP route
    • Spacetime: a reducer
    • Convex: a mutation in convex/api.ts
    • Supabase: a Postgres function at /rest/v1/rpc/<name>
  • StackBench records the requests the store's own page sends, including its auth header, and sends its request with that same signed-in session.
  • A refusal (HTTP 400, 401, 403, 404, 409, or 422, or the stack's own error) counts only after StackBench has seen the same operation succeed for an allowed customer, so a 404 from a missing route can never pass. Without that proof the result is a measurement problem.

Outside database writes

Some checks change stock directly in the database, the way another system would, and then check whether the store notices.

  • The prompt requires item, warehouse, and stock tables that the database's own tools can update.
  • How StackBench writes, by stack:
    • PostgreSQL and Supabase: an UPDATE through docker exec psql
    • MongoDB: updateOne through docker exec mongosh
    • Spacetime: an UPDATE through spacetime sql, then a SELECT to confirm it
    • Convex: the backend's admin HTTP API, called with curl

Restarts and crashes

  • A restart stops the stack and starts it again on the same data:
    • PostgreSQL, MongoDB, and Supabase: stop the store's server and run its start.sh again
    • Spacetime: restart the SpacetimeDB server
    • Convex: restart the Convex backend process
  • A crash sends SIGKILL with no warning:
    • Store's server: StackBench confirms with lsof that a process of the store's user listens on the store's port, then kills every process of that user
    • Database: StackBench kills the database's process group
  • On Spacetime, Convex, and Supabase the server logic runs inside the database, so only the database is crashed.

Lost replies

The server saves a write, but its reply never reaches the browser, as on a dropped connection.

  • Playwright intercepts every non-GET request from that customer's browser, sends it to the server itself, records the answer, and then resets the browser's connection. Incoming WebSocket messages are dropped the same way.
  • Check 203b passes only if the same cart produces one order after a lost reply, and after two submissions at once.

Data leaks

A store can send a customer's browser other customers' data, such as every order in the database, and simply not display it. Anyone can read that data in the browser's developer tools, so checking only what the page shows would miss the leak.

  • Playwright records every WebSocket frame and HTTP response body each browser receives, and decodes binary frames as UTF-8.
  • An expectNotReceived step fails if another customer's text appears anywhere in those bytes, even if the page never shows it.

03A run, start to finish

Features come in levels, and each level is one agent session.

  1. Promptfeatures for this level
  2. Agent buildsCLI via docker exec
  3. Log auditscans the CLI's session log
  4. Snapshothashes every file in /app
  5. Clean startwipe, restore, start.sh
  6. Run checksempty database per check file
  7. Unlockpassed features unlock the next level

Agent session

  • The prompt is the same on every stack except its stack setup section: connection details, the start command, and on Spacetime its SDK reference (four skill files).
  • The prompt asks for a production-quality application, but leaves out the production checks, such as permissions, live updates, and restarts.
  • StackBench runs the CLI non-interactively with docker exec, for example Claude Code with --print --bare --permission-mode acceptEdits.
  • The prompt tells the agent to reply DEPLOY_COMPLETE, or UPGRADE_COMPLETE on later levels, once the store is running. The CLI runs in print mode and exits when the agent finishes. StackBench also polls the CLI's session log for that word in case the CLI does not exit, and stops every session at 120 minutes.

Log audit

  • After each session StackBench parses the session log the CLI wrote and lists every file the agent read outside /app and every URL or socket it used in a shell command.
  • The run is thrown out as contaminated if the agent:
    • Read StackBench's checks, contracts, or prompts
    • Connected to another run
    • Fetched anything under tools/stack-bench in the SpacetimeDB repository, from GitHub or a mirror

Clean start

  • The snapshot copies /app and records a SHA-256 of every file. It leaves out:
    • node_modules
    • Build output (dist, .vite)
    • Caches
    • Logs and pid files
  • StackBench stops the store, deletes everything in /app except the agent's .git folder, copies the snapshot back, and runs start.sh as a cold start, so the store must install its own packages.
  • After startup StackBench hashes every file again and fails grading on any difference from the snapshot, so the graded code is exactly what the agent wrote.

Empty database for each check file

  • Before each check file runs, StackBench stops the store, empties the database, and starts the store again so it creates its starting data.
  • How the database is emptied, by stack:
    • PostgreSQL: dropdb --force, then createdb
    • MongoDB: db.dropDatabase() through mongosh
    • Spacetime: spacetime publish --delete-data
    • Convex: delete the backend's data folder and restart it
    • Supabase: StackBench's reset function in Postgres, then delete the storage files
  • If a check file ends with a measurement problem, StackBench empties the database and runs that file once more. If it still cannot decide, the run is thrown out and redone.

Unlocking features

Features form a dependency graph, and a feature unlocks the features built on it only when every one of its checks passes.

  • The agent never sees its results and gets no second try.

04How we know the checks work

Three controls

Before a check is trusted, StackBench runs it on every stack against three stores.

Reference storeA correct store for each stack. Every check must pass.
One seeded bugA find-and-replace edit to the reference store's source, applied one at a time. The checks it targets must fail and every other check must pass.
Empty siteA Node.js server that returns a blank page for / and 404 for everything else. Every check must fail.
  • Each seeded bug lists its edit and the checks that must catch it, and counts as caught only if a target check fails and no other check does.
  • A stack's results are published only after all three controls pass.

05Time, rate limits, and cost

Time limits

  • Each agent session ends after 120 minutes. Time a run spends paused or waiting for a grading slot does not count toward its limit.
  • These runs get an invalid outcome and are rerun, never scored:
    • Timed out
    • Hit the spending cap
    • Ended with a measurement problem

Rate limits

  • When the provider answers HTTP 429 or 529, StackBench waits 60, 120, then 300 seconds and resumes the session. After 15 minutes of waiting in total, the run pauses until an operator resumes it.

Cost

  • The broker prices each request from the token usage the provider reports, at the model's public API rates.
  • A request with no reported usage is charged its maximum, which makes that run's cost an upper bound.

06Hard questions

How is this set up?

Everything is a Docker container on one machine. The controller container runs StackBench with the host's Docker socket. For each run it starts a database container and then a coding container, a broker container that holds the model provider's API key, and a Chromium container that share the database container's network namespace, with an nftables firewall on it. The controller stays on the host network and drives Chromium with Playwright through docker exec.

How is it graded automatically?

After each session StackBench stops the store, restores the snapshot into /app, and cold-starts it with start.sh. For each check file it empties the database, restarts the store, and runs the steps with Playwright in Chromium. A feature passes when all its checks pass.

How can fixed checks find things in a store the agent designed?

The prompt lists interface names, and each becomes the selector [data-role="name"],#name. Nothing else about the page is fixed.

Can the agent see or game the checks?

No. The checks live in the controller container, which the firewall makes unreachable. Usernames change every run, and a run whose log shows it read or downloaded StackBench files is thrown out.

Can the agent test its own work?

Yes. Chromium and Puppeteer Core, a Node.js library for controlling Chromium, are installed in the coding container, and the prompt says where.

Could leftover state from the build fake a pass?

No. Grading deletes /app except .git, restores the snapshot, cold-starts the store, and fails if any file changed. Each check file starts on an emptied database.

How do you know a failure is the store's fault?

Each check passes on that stack's reference store, catches its seeded bugs, and fails on an empty site. Checks read only the listed interface names, so a different design passes as long as it behaves correctly.

What counts as a measurement problem?

Anything that stops StackBench from deciding pass or fail, such as a refusal from an operation it never saw succeed, or a broken browser or container. Those runs are thrown out and redone, never scored.

Why are the production checks left out of the prompt?

People who prompt an agent describe features, not every edge case. If the prompt listed every requirement, StackBench would only measure whether agents follow instructions.

Why does one failed check block later features?

Later features build on earlier ones. A checkout built on a cart that loses writes inherits the bug.

Does Spacetime get an advantage?

Its stack setup includes four Spacetime SDK skill files, and the other stacks get connection details only. Results describe each stack as an agent receives it.

Is writing straight to the database fair to Convex and Spacetime?

The prompt requires stock tables the database's own tools can update, and every stack's reference store passes these checks.

Does the live-update requirement favor real-time databases?

Every stack's reference store passes every live check, and polling counts if the page updates within 10 seconds. Most failing stores never refresh the page at all.

What happens when a run hits a time limit or the spending cap?

It gets an invalid outcome and is rerun.

Clockwork Labs makes Spacetime. Why trust the results?

StackBench is developed by Clockwork Labs, Convex, and Emergent. Spacetime (Clockwork Labs) and Convex are both included on the leaderboard. Every stack gets the same feature list and the same checks, and each stack's checks are proven on its own reference store.

Did every model get the same prompt?

Yes, apart from the stack setup section.

Can we read the code?

Yes. Every code chip links to the exact lines in the SpacetimeDB repository on GitHub.
