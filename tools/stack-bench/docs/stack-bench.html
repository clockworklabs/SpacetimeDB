Technical reference

StackBench

Each agent builds an online store from a feature list on one stack, and StackBench scores how many of its features hold up under production conditions.

Code excerpts are from commit 6c65947996.

Run lifecycle

The features form a dependency graph in tracks/ecommerce/progression/ecommerce.json. A feature's depth is one more than its deepest dependency.

Only a feature with status passed unlocks its dependents.

Each feature gets a status after every grade. With no repairs left, any failed check makes it failed, and its descendants become blocked. The 1.1 study plans set the repair budget to zero.

Prompt

The run rules, stack setup, and skills are shared by every session type.

The production-quality line is prepended when the plan enables it, as the 1.1 plans do.

A build or upgrade session then adds the task line, the feature texts, the starting catalog, and the application interface.

The 1.1 runs use the neutral-dev profile. Every stack gets connection details only, and Spacetime also gets three SDK skills and a workflow note.

Production checks are scored without being stated. Their specifications are added to the expected set, which never reaches the prompt.

Sandbox

The build container drops all capabilities and adds back six file and process capabilities, runs read-only, and mounts the store directory.

It also mounts the transcript folder and the mounts the stack adapter declares. For Spacetime those are the read-only SDK and CLI.

The network namespace drops all traffic by default, rejects the host and private and reserved ranges, and allows public HTTP and HTTPS.

Subagents are always refused. Web search is off unless a study enables it, and it cannot be enabled for Claude Code. It was off for every 1.1 run.

After every coding session, a transcript audit flags reads of StackBench files and network escapes. A serious hit marks the run contaminated.

Model access, time, and spending

Provider keys stay in a broker. Before forwarding a request, the broker reserves the request's worst-case cost and refuses it with HTTP 402 if the run's cap cannot cover it.

Each coding session has a 120-minute limit.

The run limit excludes planned pauses and grading-slot waits.

Throttled requests wait 60, 120, then 300 seconds. The next wait would pass the 15-minute cap, so the session then holds for an operator.

The credential profile is chosen per attempt, then per adapter, then the default, and stays fixed for the run.

Grading

Every grade rebuilds the store from its saved source. Any file that differs from the snapshot stops the grade.

Checks run in Chromium through Playwright. An assertion with no timeout of its own waits 5 seconds.

A direct server call replays the request with the browser's own session credentials.

A refusal on a route that never accepted a valid call is inconclusive, so a missing route cannot pass as a permission refusal.

Direct stock writes bypass the store. Spacetime uses spacetime sql, then reads the row back.

PostgreSQL and Supabase share one psql writer, MongoDB uses mongosh, and Convex uses its admin API.

A restart goes through the stack's lifecycle adapter.

A crash sends SIGKILL to the application or the database. On Spacetime, Convex, and Supabase the application and database are one process, so only the database crash applies.

Lost-reply checks forward each write to the server, then reset the browser's connection before it sees the reply. Inbound WebSocket messages are dropped while armed.

Privacy checks record every WebSocket frame a browser receives.

Checks

A check is a list of steps in a scenario file. This is the outside-write stock alert check: stock is written to the database, and a fresh sign-in must show the alert within 75 plus 15 seconds.

Outcomes and scoring

Each check ends with one of five statuses. Passed adds its points, failed and blocked add zero, and inconclusive or harness failure invalidates the run.

Invalid runs are excluded when results are published.

A feature earns the points of its passed checks. A blocked feature earns zero, and its points stay in the denominator.

How checks are proven

A seeded bug is a find-and-replace edit to a reference app, with the checks it must fail.

It is caught only when its targets fail at an assertion, no other check regresses, and nothing is inconclusive.

The empty app serves a blank page and returns 404 for everything else. Every scored check must fail on it.

The calibration's check list must equal the graph's checks through depth 3, and qualification fails unless every seeded bug is caught.

Each pack's time budget is twice its slowest reference run, rounded up, and never below its declared waits.

Cost

The broker adds each request's cost from reported usage at API list rates. OpenRouter requests use the cost the provider reports. A request without usage is charged its reserved ceiling.

Charging a ceiling makes the run's cost an upper bound.

Study design

Runs launch from one list of every model on every stack. Each of the three rounds starts one place further down that list, so the same model on the same stack is never always launched first.

FAQ

Clockwork Labs makes Spacetime. Why trust the results?

StackBench is developed by Clockwork Labs, Convex, and Emergent. Spacetime (Clockwork Labs) and Convex are both included on the leaderboard. Every check runs unchanged on all five stacks against each stack's reference app, seeded bugs, and empty app. See How checks are proven.

Can an agent see the checks?

No. The sandbox mounts the store, transcripts, and stack SDK only, and a transcript audit after every session catches reads of StackBench files. See Sandbox.

Does the live-update requirement favor real-time databases?

Every stack's reference app passes every live check. Of the 43 stores that fail the live support-case check, 40 never update the customer's open page.

Are three runs enough?

They separate the stacks, but not models a few points apart. GPT-6.1 Sol's three Spacetime runs scored 113, 176, and 177 points.
