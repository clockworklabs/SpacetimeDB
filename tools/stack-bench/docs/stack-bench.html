Technical reference

StackBench

Each agent builds an online store from a feature list on one stack, and StackBench scores how many of its features hold up under production conditions.

The code below is from commit 6c65947996.

How a run works

Features unlock in levels. Level 1 features need nothing else. Every other feature comes one level after the last thing it needs, so checkout, which needs the cart, comes after the cart. The features and what each one needs are listed in tracks/ecommerce/progression/ecommerce.json.

A feature unlocks the features built on it only when every one of its checks passes.

After each round of grading, a feature with any failed check is marked failed, and everything built on it is marked blocked. In 1.1 the agent gets no chance to fix failures.

What the agent is told

Every prompt starts with the same basics: where to put the code, how to start it, the stack's connection details, and for Spacetime its SDK docs.

In 1.1 the prompt also opens with this line.

Then come the instructions for this round, the features to build, the starting products, and the IDs of the buttons and fields StackBench uses.

Every stack gets the same kind of setup notes. Spacetime is the only stack that also gets SDK docs.

The production requirements are graded but never written into the prompt. This is the code that keeps them out.

Where the agent works

The agent works in a locked-down container. It can't change the system, and the only folder it can write to is the store's code folder.

It also gets its own log folder, and on Spacetime a read-only copy of the SDK and CLI.

The container gets 2 CPUs and 4 GB of memory.

It can reach the public web, but not the host machine, the local network, or other runs.

Agents can't start helper agents. Web search was off for every 1.1 run.

After every session, StackBench reads the agent's log. If the agent looked at StackBench's own files, the run doesn't count.

API keys, time limits, and spending

The agent never holds the API key. Its requests go through a proxy that refuses any request that could push the run past its spending cap.

A coding session can last two hours.

A whole run can last four hours. Time spent waiting for a free grading slot doesn't count.

When a provider rate-limits the agent, StackBench waits 1 minute, then 2, then 5. If the agent is still blocked, the run pauses until someone resumes it.

Each run uses one account for its whole duration.

How StackBench tests the store

Every test starts the store from its saved code. If the code doesn't match what was saved, the test stops.

StackBench drives Chromium with Playwright. Unless a check says otherwise, it gives the page 5 seconds to show what it's looking for.

To test the server directly, StackBench sends requests with the signed-in user's own session, the same way the browser does.

If the server rejects a request and StackBench never saw that endpoint work, the check counts as neither a pass nor a fail, because the endpoint might simply not exist.

To change stock behind the store's back, StackBench writes to the database directly. On Spacetime it runs SQL and reads the row back to confirm.

PostgreSQL and Supabase use psql, MongoDB uses mongosh, and Convex uses its admin API.

Restarts use each stack's own restart command.

Crash tests kill the app or the database outright. On Spacetime, Convex, and Supabase the app and the database run as one process, so StackBench kills that one process.

To test lost replies, StackBench lets a write reach the server, then cuts the browser's connection before the reply arrives.

For privacy checks, StackBench records everything the server sends each browser, including data the page never shows.

What a check looks like

A check is a list of steps in a JSON file. In this one, StackBench changes the stock directly in the database, waits 75 seconds, signs the customer in again, and expects the stock alert to appear within 15 seconds.

Results and points

Each check ends one of five ways. A pass earns its points. A fail, or a check skipped because its feature never unlocked, earns nothing. If StackBench couldn't measure the check, or broke itself, the whole run is thrown out and redone.

Thrown-out runs are left out of the published results.

A feature scores the points of its checks that passed. A feature that never unlocked scores zero, but its points still count toward the total.

How we know the checks work

Each stack has a working reference store that passes every check. To prove a check catches what it should, StackBench breaks that store on purpose. Each seeded bug is a small code edit, listed with the checks that should catch it.

A seeded bug only counts as caught if the checks it targets fail and nothing else breaks.

StackBench also tests an empty site that serves a blank page. Every check has to fail on it, so no check can pass by accident.

Before results are official, the list of checks has to match the feature list exactly, and every seeded bug has to be caught.

Each group of checks has a time limit of twice the slowest time the reference store took.

Cost

Cost comes from the token counts the provider reports, at the provider's public API prices. If a request never reports its usage, StackBench charges the most it could have cost.

When that happens, the run's cost is marked as an upper bound. These are the reasons it can happen.

Run order

Runs launch from one list of every model on every stack. Each of the three rounds starts one place further down that list, so no model and stack pair always launches first.

FAQ

Clockwork Labs makes Spacetime. Why trust the results?

StackBench is developed by Clockwork Labs, Convex, and Emergent. Spacetime (Clockwork Labs) and Convex are both included on the leaderboard. Every check runs the same way on all five stacks, and each stack has its own reference store, seeded bugs, and empty site to prove the checks. See How we know the checks work.

Can an agent see the checks?

No. The agent's container only has the store's code, its log folder, and the stack's SDK. StackBench also reads the agent's log after every session to catch it looking at StackBench files. See Where the agent works.

Does the live-update requirement favor real-time databases?

Every stack's reference app passes every live check. Of the 43 stores that fail the live support-case check, 40 never update the customer's open page.

Are three runs enough?

They separate the stacks, but not models a few points apart. GPT-6.1 Sol's three Spacetime runs scored 113, 176, and 177 points.
