A benchmark you can rerun, inspect, and trust.

Stack Bench is a controlled evaluation appliance for AI-generated application stacks. It asks an agent to build the same product on different backends, verifies real behavior in Docker, and preserves the exact inputs, evidence, time, cost, and failures behind every result.

The 60-second version

The product is no longer a one-off scoreboard. It is becoming a repeatable way to measure how well a model can build, repair, and preserve guarantees on a chosen stack.

The problem

Sequential demos produced interesting numbers, but mutable inputs, contaminated agents, stale artifacts, host differences, and weak test oracles made the old comparisons impossible to reproduce confidently.

The product

A run selects an exact recipe, stack, agent/model, scope, and repetition policy. The app is generated in isolation, exercised through real browsers and backend controls, and recorded as structured evidence.

The value

It measures more than feature completion: first-try quality, repair cost, regressions, durability, authorization, contention, deploy windows, and whether the measuring instrument itself behaved correctly.

How one run works

Every step is tied to an exact run identity. Missing or malformed evidence fails closed instead of becoming a score.

Choose

Select the product recipe, capability packs or checks, backend, model/agent, and repetitions.

Resolve

Compile exact pack, fixture, prompt, contract, scoring, calibration, and selection identities.

Isolate

Acquire a private backend lease and immutable build container. Refuse foreign resources.

Build

Give the agent the task and stack guidance. Preserve the unaided first attempt and its complete cost ledger.

Verify

Reset safely, lint the contract, drive isolated browser actors, and test direct database and lifecycle behavior.

Repair

Optionally send sanitized behavioral failures back to the agent, then regrade without hiding regressions.

Compare

Publish structured artifacts and compare only runs with matching recipe and selected-scope identities.

What is already configurable

  • Application track and exact recipe version
  • Behavior packs or individual stable checks
  • Starting fixture version
  • Backend and run index
  • Agent adapter, model, fix-round cap, and evidence scope
  • Intentional subsets, recorded as exactly what ran

Capabilities now own both sides

A capability pack owns its public requirement fragments, testing-hook fragments, and checks. Add the pack and all three appear; remove it and its unique material disappears. Check-only filters narrow measurement without quietly changing the app's task.

Concrete example: session durability is now separate from ordinary account access. Removing it removes the reload/reconnect instruction and three checks while signup, credentials, and account-required behavior remain.

What the coding agent receives

The benchmark must define the job precisely without exposing the answer key. Every behavior-affecting input is preserved with the run, so a later reader can tell exactly what was prescribed.

Short answer on schema We describe the product's entities, relationships, rules, starting records, and required write-action names. For ecommerce L1 we also prescribe three interoperability tables—item, warehouse, and stock—so the same external database-write test has a stable target on every backend. The agent designs the rest of the domain schema, indexes, reducers or routes, authorization, transactions, subscriptions, and reconciliation logic.

Prescriptive inputs we intentionally provide

  • Product requirements: the visible features, roles, business rules, error behavior, and real-time guarantees for the selected level.
  • UI and accessibility expectations: layout, states, basic visual language, keyboard behavior, and exact data-testid hooks used by browser automation.
  • Named write surface: required ordinary API route or reducer names for operations that the harness must replay concurrently or with hostile credentials.
  • Starting fixture: exact items, prices, categories, warehouse quantities, seeded roles, and intentionally empty collections. Fixture identity is versioned.
  • Backend build contract: assigned ports, database or module name, connection address, required app title, project layout, install/build/deploy commands, and disposable-data policy.
  • Comparison stack when prescribed: PostgreSQL and MongoDB can be assigned Express, Socket.io, React, and a selected ORM; SpacetimeDB can be assigned its TypeScript module and client SDK. The exact backend guidance is versioned separately from the requested product behavior.
  • API reference where training data is weak: selected SpacetimeDB server/client skill documents are inlined and recorded. They explain supported APIs; they do not contain benchmark answers.
  • Execution protocol: work in the isolated app directory, bind dev servers correctly, run the opaque contract-lint command, leave the service running, and emit a completion marker.

What we deliberately do not provide

  • The hidden scenario files, browser action plan, point values, expected evidence, grader implementation, or score thresholds
  • A completed domain schema beyond the three stock interoperability tables, or any authorization policy, transaction design, subscription design, or application source code
  • The canonical reference applications, seeded mutations, null control, or known backend-specific failure list
  • Another backend's implementation instructions or a migration recipe that reveals how to translate the solution
  • Unrequested repair hints during the first attempt; that unaided build is preserved before any optional fix round

After grading: if repair rounds are part of the declared experiment, the agent receives a sanitized behavioral bug report: expected behavior, observed behavior, and useful evidence. It still does not receive grader source or hidden checks.

Fixed for fairness

The product requirements, fixture, scoring recipe, container, budgets, and run policy must match across stacks unless the experiment explicitly declares a different treatment.

Backend-specific by necessity

Connection details, project layout, deploy commands, SDK reference, and branded title differ because those are the actual developer surfaces being measured. Their exact bytes are part of provenance.

Left to the agent

Data modeling, code organization inside the contract, authorization mechanics, transaction boundaries, live-update design, error handling, and how to make every stated guarantee hold.

Two independent choices: what to build and how much stack help to give

Requested behavior

Select capability packs such as account access, session durability, cart/checkout, or inventory operations. Adding or removing a pack changes both the product request and its matching checks. A check-only filter narrows measurement without changing the request.

Backend guidance

Prescribed names the framework and implementation guidance. Neutral supplies only access facts and API reference, without framework or architecture advice. The prescribed profile is qualified; the symmetric neutral profile is implemented and prompt-snapshotted but remains draft.

Unmentioned defaults probes

The design reserves a separate, first-build-only probe channel for behavior such as durability or reconnect handling that was not requested. Probe evidence will never affect requested-feature score or enter repairs. The separation is enforced now; non-empty probe execution is still future work.

Composition is now end to end for ecommerce Ordered source fragments reconstruct the legacy full L1 and L2 task text byte-for-byte. Shared fragments must match exactly, and the compiled release records independent requirement, contract, and combined-task hashes. Chat remains on the legacy whole-level authoring model until it is migrated.

What features and guarantees we test

Requirements say what the app must do. Hidden tests establish whether it really does it. Diagnostic controls establish whether the test itself can be trusted.

Feature checks

Can a real user complete the promised workflow, and do all affected views update? Examples: create an account, buy an item, transfer stock, ship an order, or invite a room member.

Guarantee checks

Does the server preserve authorization, ownership, accounting, isolation, durability, and atomicity when clients lie, race, disconnect, or bypass the UI? Higher levels rerun inherited guarantees.

Instrument controls

Can known-good references pass, does a blank app score zero, and does each seeded defect fail the exact intended criterion? A control failure blocks publication rather than becoming an app score.

How we got here

The history matters because most of the current product shape came from invalid runs and false conclusions, not from a clean greenfield design.

Jun-Jul

The predecessor: sequential upgrades

We learned that an agent could carry applications through a ladder of levels and added a third backend. The runs were useful exploration, but their exact inputs and evidence cannot be reconstructed today.

Aug 4

Stack Bench begins as a real harness

Functional browser grading, mutation testing, separate feature/guarantee axes, per-run databases, a model-free loop fixture, and levels organized by verifiable properties appeared together.

Aug 6

Every earlier score was voided

Transcript audits showed generated apps reading scenarios, grader code, contracts, and notes. The lesson was foundational: the agent will optimize against anything it can see, and contamination can be asymmetric.

Aug 7-9

The cost thesis changed

Feature scores saturated. Cost analysis showed that code volume was not the driver; repeated context reads, compiler failures, source-diving, and repair turns were. The benchmark shifted from scoreboard to product-friction instrument.

Aug 10

Isolation and measurement failures ate real runs

Container attempts initially failed, fix-round comparison treated a changed denominator as regression, and the first build was being overwritten. The harness moved to Docker-only builds, preserved unaided attempts, and gained authenticated leases and cleanup controls.

Aug 10-11

The instrument found and helped verify real product defects

Cost and failing guarantees led back to reconnect identity loss on the recommended client path. Separately, the Docker log-stream warning was proven to be a real spacetime dev authorization defect; the CLI identity handoff was fixed and the reproduction made mandatory.

Aug 11

References, mutations, null controls, and Docker qualification

Preserved reference apps became byte-bound and buildable. Repeated live Docker gates exposed reset, timeout, mutation, and oracle defects. Candidate references passed, but later executable changes mean they must be qualified again before publication.

Aug 12

From scripts to versioned product contracts

Packs, recipes, fixtures, calibration, exact selection, artifact envelopes, and the 47-action registry landed. All 47 actions now run through independent capability-scoped executors; the central compatibility dispatcher is gone.

Aug 13

The first qualified baseline

Promoted ecommerce L1 1.0 and L2 1.1 gained repeated Docker reference, mutation, and null evidence for MongoDB, PostgreSQL, and SpacetimeDB. Campaign admission, checkpointing, failure retention, correction accounting, reporting, and the Linux appliance were hardened around those controls.

Aug 14-15

Composable study conditions and framework-neutral candidates

Requested behavior became independently selectable by pack, while prescribed versus neutral backend guidance became a separate versioned study axis. Framework-neutral L1 1.1 and L2 1.2 keep the same execution/scoring but remove shared framework advice. Both candidates have now completed all 13 fresh qualification evidence slots without silently changing the public aliases.

Changes to the actual SDK and CLI

These are product-code outcomes prompted by the benchmark. They are separate from changes that only hardened Stack Bench.

TypeScript SDK · committed

Automatic reconnect preserves the issued identity

A first-time anonymous client originally built its connection before it had a token. Automatic reconnect rebuilt from that stale tokenless builder, so the host correctly minted a new identity and the user's identity-owned rows appeared to vanish.

Change: ConnectionManager now reapplies the last issued token on automatic reconnect and zombie-socket revival. Explicit rebuild() still honors the caller's token, preserving login, token-swap, and logout semantics.

Commit 1f77a6985; regression tests cover token reuse and explicit rebuild, and bb2ab57ee verifies identity continuity across a real host restart.

TypeScript bindings · committed

Table reference errors name the type

TableRef was an anonymous readonly object type. TypeScript therefore expanded its internal structure in constraint errors, producing hundreds of characters of nested generated types that agents carried through later calls.

Change: it is now a named interface, so errors identify TableRef<...> instead of dumping its internals. The runtime shape is unchanged.

Also in 1f77a6985; regression tests require the named type and enforce a readable error-length bound.

CLI · committed on this branch

spacetime dev keeps publish authorization for logs

On a clean config, programmatic publish logged in using a cloned Config. The long-running dev process remained tokenless, logged in again for its log stream as a different identity, and was correctly denied access to the database it had just published.

Change: the programmatic publish helper takes &mut Config, and dev passes its live config through initial publish and rebuilds. The publisher's token is therefore retained for log authorization.

Commit 00372a166 contains the branch's integrated change. The CLI library suite passed 169 tests, and the unchanged Docker reproduction requires logStreamingAuthorized: true.

Why this distinction matters Stack Bench did not merely generate a score. It produced reproducible failures, narrowed the mechanisms, drove changes in real SDK/CLI code, and converted the original reproductions into regression coverage. The benchmark results and the product-code changes remain separately versioned so neither can be mistaken for the other.

Hypothesis killed: “the skill documents are the cost”

The larger guidance pack was measurable, but only about $0.18 in the analyzed run—roughly 1.6% of that bill. The expensive behavior was the agent having to search SDK and generated-binding source to discover missing facts, then carrying that investigation through later calls.

Product implication: better API shape, actionable errors, and concise documentation can reduce attempts and accumulated context more than simply shortening the prompt.

First try matters more than repair

Early fix-loop data showed most gains in round one and little or no gain later. Some rounds chased inconclusive evidence or harness wording rather than defects. The unaided build became a first-class artifact because it explains both first-try quality and most of the downstream repair cost.

Product implication: the useful metric is not only final score; it is first-try correctness, cost to reach a stable result, and guarantees retained during repair.

What the benchmark taught us

These are product lessons from building the instrument, not backend marketing claims.

Features and guarantees are different axes

An app can pass new feature tests while breaking old promises. One historical MongoDB L2 build passed 54/54 new checks while losing two inherited L1 guarantees. Higher levels must rerun lower-level guarantees.

Functional full marks can hide deploy failures

Two PostgreSQL shops could look equivalent in feature grading while only one survived an out-of-band write during an app-server outage. Durability and reconciliation need lifecycle tests, not another happy-path click.

The oracle can lie both ways

A blank app scoring zero is necessary but insufficient. A good app can fail an over-constrained assertion, and a broken app can pass a vacuous one. Reference apps, null controls, and exact seeded mutations are all required.

Inconclusive is not failure

If the harness could not observe a transport, acquire a resource, or keep a browser alive, that absence of evidence cannot become an application defect or a point. Outcomes are now structured separately.

Isolation is an integrity feature

The agent once read the answer key through ordinary file search. Docker-only generation, hidden grader inputs, exact backend leases, and secret-safe artifacts are part of measurement correctness—not deployment polish.

Benchmarking can be product discovery

The strongest output was not a score: failing first-try guarantees and cost traces led to a real reconnect identity defect, while unchanged Docker reproduction isolated a separate development log-authorization defect.

What exists today

The distinction below is intentional: working engineering infrastructure is not the same thing as a frozen, qualified benchmark release.

Working and verified

  • Docker-only coding sessions; no host-generation fallback
  • Authenticated leases, dedicated resources, collision refusal, and tested teardown
  • Strict artifact schema with run ancestry, timestamps, exact component identities, and secret rejection
  • Versioned ecommerce L1/L2 packs, pack-owned task fragments, recipes, fixtures, exact selection, calibration, and promotion lifecycle
  • Pack/check-scoped runs that record exactly what was requested, attempted, and not run
  • 47 registered actions with input schemas, capabilities, deadlines, evidence, and redaction metadata
  • All 47 actions have independent capability-scoped executors; no central compatibility dispatcher remains
  • Typed evidence drives scoring, null/mutation controls, comparison, repair selection, and reporting; diagnostic wording does not decide outcomes
  • Versioned stack adapters for three measured backends plus a deterministic test stack; versioned agent adapters for coding, deterministic, fault, and reference paths
  • Operator preflight, pinned Linux/amd64 controller appliance, immutable campaign plans, resumable execution, and reproducible HTML reporting
  • 337/337 automated tests pass on the host, including two live Playwright grades; the exact post-commit Linux controller is rebuilt and rerun for each evidence commit
  • Real Docker smoke publishes a TypeScript module, verifies SQL and watcher health, and requires authorized logs
  • Promoted L1/L2 baseline evidence remains valid; framework-neutral L1 1.1 and L2 1.2 each have fresh 13/13 qualification evidence without moving either default alias
  • For every L2 stack, two stable pristine repetitions scored 55/55 plus 20/20 inherited; two mutation repetitions each caught all 3/3 declared defects, and the null control failed every scored criterion

Still required for production quality

  • Review the now-complete framework-neutral qualification evidence and deliberately decide whether L1/L2 aliases and governance states should move
  • Run a frozen repeated three-stack model campaign under declared prescribed and/or neutral conditions and publish dispersion, invalid-run rate, cost, and evidence limitations
  • Resolve the remaining point-bearing statedBy warnings and add exact mutants before promoting currently diagnostic zero-point checks
  • Implement non-empty first-build defaults probes for unmentioned durability/reconnect behavior without feeding those results into score or repairs
  • Move active scenario bodies from the strict compatibility executor into the general recipe executor; migrate chat into pack/recipe composition
  • Package adapters as separately identified releases, finish CI tiers/replay, and complete distributable registry/SBOM/signature material when an external release is actually needed
  • Only after the frozen L1/L2 campaign is reproducible should validated coverage expand beyond L2

Recommended path from here

The model-free qualification boundary is complete. Freeze the candidate governance and experiment protocol before buying model runs so every measured attempt belongs to one declared comparison.

1

Freeze the qualified candidate

Review the complete L1/L2 evidence, decide whether to move aliases and governance states, and lock the exact recipe, packs, fixtures, calibration, images, adapters, and prompts used by the campaign.

2

Run the real comparison

Freeze the exact stacks, model/agent, prescribed or neutral condition, selected packs, repetitions, ordering, budgets, and retry rules. Run the full matrix and publish raw evidence plus variability and invalid-run rate.

3

Finish the handoff

Exercise the appliance from a second clean runner, close the remaining authoring/replay gaps, document the operator path, and only then extend qualified workloads beyond L2.

The meeting decision Agree that v1 is a reproducible evaluation appliance—not “all five levels.” The v1 finish line is: configurable requirements and checks, one Docker path, typed evidence, versioned stack/model adapters, operator preflight, and a frozen repeated L1/L2 campaign whose raw artifacts can be independently inspected.
