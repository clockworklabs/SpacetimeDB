An audit showed that the coding workspace and testing workspace were not isolated well enough. We stopped using those scores and moved generation into Docker with the independent test system outside the coding environment.

Where the project stands now

This is the current verified state. Superseded run numbers are intentionally omitted.

The problem

Sequential demos produced interesting numbers, but mutable inputs, contaminated agents, stale artifacts, host differences, and weak test oracles made the old comparisons impossible to reproduce confidently.

The product

A run selects an exact recipe, stack, agent/model, scope, and repetition policy. The app is generated in isolation, exercised through real browsers and backend controls, and recorded as structured evidence.

The value

It measures more than feature completion: first-try quality, repair cost, regressions, durability, authorization, contention, deploy windows, and whether the measuring instrument itself behaved correctly.

How one run works

Every step is tied to an exact run identity. Missing or malformed evidence fails closed instead of becoming a score.

Choose

Select the product recipe, capability packs or checks, backend, model/agent, and repetitions.

Resolve

Compile exact pack, fixture, prompt, contract, scoring, calibration, and selection identities.

Isolate

Acquire a private backend lease and immutable build container. Refuse foreign resources.

Build

Give the agent the task and stack guidance. Preserve the unaided first attempt and its complete cost ledger.

Verify

Reset safely, lint the contract, drive isolated browser actors, and test direct database and lifecycle behavior.

Repair

Optionally send sanitized behavioral failures back to the agent, then regrade without hiding regressions.

Compare

Publish structured artifacts and compare only runs with matching recipe and selected-scope identities.

What is already configurable

  • Application track and exact recipe version
  • Behavior packs or individual stable checks
  • Starting fixture version
  • Backend and run index
  • Agent adapter, model, fix-round cap, and evidence scope
  • Intentional subsets, recorded as exactly what ran

Capabilities now own both sides

A capability pack owns its public requirement fragments, testing-hook fragments, and checks. Add the pack and all three appear; remove it and its unique material disappears. Check-only filters narrow measurement without quietly changing the app's task.

Concrete example: session durability is now separate from ordinary account access. Removing it removes the reload/reconnect instruction and three checks while signup, credentials, and account-required behavior remain.

What the coding agent receives

Every run saves the exact build brief, backend guidance, and repair messages, so anyone reviewing the result can see what the coding agent was asked to do.

Short answer on schema We describe the product's entities, relationships, rules, starting records, and required write-action names. For ecommerce L1 we also prescribe three interoperability tables—item, warehouse, and stock—so the same external database-write test has a stable target on every backend. The agent designs the rest of the domain schema, indexes, reducers or routes, authorization, transactions, subscriptions, and reconciliation logic.

Included in the build brief

  • Product requirements: the visible features, roles, business rules, error behavior, and real-time guarantees for the selected level.
  • UI and accessibility expectations: layout, states, basic visual language, keyboard behavior, and exact data-testid hooks used by browser automation.
  • Named write surface: required ordinary API route or reducer names for operations that the harness must replay concurrently or with hostile credentials.
  • Starting fixture: exact items, prices, categories, warehouse quantities, seeded roles, and intentionally empty collections. Fixture identity is versioned.
  • Backend build contract: assigned ports, database or module name, connection address, required app title, project layout, install/build/deploy commands, and disposable-data policy.
  • Optional implementation guidance: a run can name frameworks and libraries, or name only the backend and connection details. This choice is saved separately from the product brief.
  • API reference where training data is weak: selected SpacetimeDB server/client skill documents are inlined and recorded. They explain supported APIs; they do not contain benchmark answers.
  • Execution protocol: work in the isolated app directory, bind dev servers correctly, run the opaque contract-lint command, leave the service running, and emit a completion marker.

Kept in the independent test system

  • The browser and backend test steps, scoring rules, and expected evidence
  • The known-good, deliberately broken, and blank apps used to validate each test
  • Backend-specific test controls and the test runner implementation
  • Comparison logic that decides whether a run is complete enough to publish

After testing: if repair rounds are enabled, the agent receives a plain bug report describing the expected behavior, observed behavior, and useful evidence. The original build remains saved separately.

Fixed for fairness

The product requirements, starting data, scoring rules, container, budgets, and run policy must match across stacks unless the run explicitly records a different setup.

Backend-specific by necessity

Connection details, project layout, deploy commands, SDK reference, and branded title differ because those are the actual developer surfaces being measured. Their exact bytes are part of provenance.

Left to the agent

Data modeling, code organization inside the contract, authorization mechanics, transaction boundaries, live-update design, error handling, and how to make every stated guarantee hold.

Choices that can be mixed and matched

Product features

Select what the agent must build: accounts, catalog, purchasing, cart/checkout, reviews, and warehouse administration. Each versioned feature owns its prompt fragment, public interface, and checks.

Quality checks

Select production qualities such as access control, durability, live updates, concurrency safety, and transaction safety. For each run, choose whether each quality belongs in the build brief, the scored tests, both, or neither.

Backend guidance

Choose how much technical direction the coding agent receives. A detailed brief can name frameworks and libraries. A minimal brief names the backend, connection details, and relevant API reference while leaving the architecture to the agent.

Extra measurements

A run may also record clearly labeled measurements that do not affect its score or repair loop. These are kept separate from the comparison result. Every shared check still has to be validated on MongoDB, PostgreSQL, and SpacetimeDB before use.

Composition is now end to end for ecommerce Ordered source fragments reconstruct the legacy full L1 and L2 task text byte-for-byte. Shared fragments must match exactly, and the compiled release records independent requirement, contract, and combined-task hashes. Chat remains on the legacy whole-level authoring model until it is migrated.

What features and guarantees we test

Requirements say what the app must do. Independent verification establishes whether it really does it. Diagnostic controls establish whether the test itself can be trusted.

Feature checks

Can a real user complete the promised workflow, and do all affected views update? Examples: create an account, buy an item, transfer stock, ship an order, or invite a room member.

Guarantee checks

Does the server preserve authorization, ownership, accounting, isolation, durability, and atomicity when clients lie, race, disconnect, or bypass the UI? Higher levels rerun inherited guarantees.

Instrument controls

Can known-good references pass, does a blank app score zero, and does each seeded defect fail the exact intended criterion? A control failure blocks publication rather than becoming an app score.

What actually runs—not just what the JSON declares

The JSON is only the versioned test plan. The executable is JavaScript backed by Playwright and stack adapters. It resets the real benchmark database, opens the generated application, performs actions as isolated users, disturbs the running system, observes the result, and only then creates a score.

StageWhat the runner physically doesWhat prevents a false result
1. PrepareVerify that the app points at the benchmark-owned database, reset that database, restart when reseeding requires it, and wait for the app to answer.The runner aborts instead of grading a foreign database, a failed reset, or source left mutated by an interrupted control run.
2. Check the interfaceOpen the app and verify the required data-testid hooks and named write actions. These are the controls the independent tests will use.Missing controls are reported explicitly. A test the harness cannot issue becomes inconclusive, not an application failure.
3. Create usersLaunch Chromium and create a separate Playwright browser context for every actor in the feature. Each context has isolated cookies, local storage, network traffic, trace, and optional video.One simulated user's identity cannot leak into another user's session. Every feature also uses run-scoped account and room names.
4. Arrange stateRun setup actions through the UI or the declared stack action. Setup creates users, signs them in, navigates views, and establishes the exact state needed by the check.A failed setup makes the check untestable; it does not masquerade as a behavioral assertion failure.
5. Apply pressureClick in several browsers at once, send authenticated writes at once, replay captured requests under another identity, change the database out of band, disconnect clients, or stop/restart the app or backend.Concurrency first confirms that every target is ready, then dispatches with Promise.all. If fewer than two operations reach the server, the race is inconclusive.
6. ObserveRead exact DOM values from open clients, inspect HTTP and WebSocket traffic delivered to each actor, and when required open a fresh browser to verify committed state.The grader never reloads during a live-update assertion. One isolated browser per user

grader/grade.mjs creates fresh browser storage and a real page for every actor named by the selected feature.

for (const name of feature.actors) {
  const context = await browser.newContext(
    args.media ? { recordVideo: { dir: args.media,
      size: { width: 1280, height: 800 } } } : {}
  );
  if (args.trace) await context.tracing.start({
    screenshots: true, snapshots: true
  });
  const page = await context.newPage();
  page.setDefaultTimeout(DEFAULT_WITHIN);
  await page.goto(args.url, {
    waitUntil: 'domcontentloaded', timeout: 20000
  });
  const actor = new Actor(name, page, context);
  actor.annotate = Boolean(args.media);
  actors.set(name, actor);
  contexts.push({ context, name, page });
}

Evidence decides the point

grader/grade.mjs executes every step through the registered action contract, builds typed criterion evidence, then scores that evidence.

for (const step of criterion.steps) {
  activeActor = step.actor ?? activeActor;

    { feature: feature.name, criterion: criterion.id,
      step: describeStep(step) }

}

A complete example: six customers race for three cameras

What happens on the machine

  1. The ecommerce database is reset to its seed, where the Mirrorless Camera has three units.
  2. Chromium opens six isolated sessions. The runner signs up six scoped customers and takes each to the camera.
  3. The runner waits until all six Buy buttons are visible and enabled.
  4. It dispatches all six clicks together, without waiting for one purchase to finish before starting the next.
  5. After the contention settles, it reads the stock shown to actor A and requires exactly 0.
  6. It reads the same stock field in all six still-open browsers and requires numeric agreement without reloading them.
  7. The action evidence, timings, observations, screenshots on failure, and final criterion evidence are written into the grade artifact.

Exactly what that score proves

The current point-bearing check proves that the six-way rush leaves stock at exactly zero and that all six open clients agree on that number. Its backend-specific mutants are used during qualification to verify that the oracle notices a broken reservation/concurrency implementation.

It does not yet award points for the population-wide order count or exact revenue total. Those checks remain visible candidates until deliberately broken reference apps prove that each test catches the intended defect.

That is the level of precision the result bundle retains: which behavior ran, how it was exercised, what was observed, whether the instrument completed, and whether the observation contributed to the score.

Some systems and contention checks intentionally carry zero points while their oracle or mutation evidence is still being qualified. They remain visible diagnostics; they cannot quietly inflate or reduce a published score.

Product changes that came out of the work

These are product-code outcomes prompted by the benchmark. They are separate from changes that only hardened Stack Bench.

TypeScript SDK · committed

Automatic reconnect preserves the issued identity

A first-time anonymous client originally built its connection before it had a token. Automatic reconnect rebuilt from that stale tokenless builder, so the host correctly minted a new identity and the user's identity-owned rows appeared to vanish.

Change: ConnectionManager now reapplies the last issued token on automatic reconnect and zombie-socket revival. Explicit rebuild() still honors the caller's token, preserving login, token-swap, and logout semantics.

Commit 1f77a6985; regression tests cover token reuse and explicit rebuild, and bb2ab57ee verifies identity continuity across a real host restart.

TypeScript bindings · committed

Table reference errors name the type

TableRef was an anonymous readonly object type. TypeScript therefore expanded its internal structure in constraint errors, producing hundreds of characters of nested generated types that agents carried through later calls.

Change: it is now a named interface, so errors identify TableRef<...> instead of dumping its internals. The runtime shape is unchanged.

Also in 1f77a6985; regression tests require the named type and enforce a readable error-length bound.

CLI · committed on this branch

spacetime dev keeps publish authorization for logs

On a clean config, programmatic publish logged in using a cloned Config. The long-running dev process remained tokenless, logged in again for its log stream as a different identity, and was correctly denied access to the database it had just published.

Change: the programmatic publish helper takes &mut Config, and dev passes its live config through initial publish and rebuilds. The publisher's token is therefore retained for log authorization.

Commit 00372a166 contains the branch's integrated change. The CLI library suite passed 169 tests, and the unchanged Docker reproduction requires logStreamingAuthorized: true.

Why this distinction matters Stack Bench did not merely generate a score. It produced reproducible failures, narrowed the mechanisms, drove changes in real SDK/CLI code, and converted the original reproductions into regression coverage. The benchmark results and the product-code changes remain separately versioned so neither can be mistaken for the other.

What the benchmark taught us

These are product lessons from building the instrument, not backend marketing claims.

New features can break old behavior

An app can pass the checks for a new feature while breaking behavior from an earlier level. Every higher level must rerun the earlier checks instead of assuming they still work.

Functional full marks can hide deploy failures

Two PostgreSQL shops could look equivalent in feature grading while only one survived an out-of-band write during an app-server outage. Durability and reconciliation need lifecycle tests, not another happy-path click.

The oracle can lie both ways

A blank app scoring zero is necessary but insufficient. A good app can fail an over-constrained assertion, and a broken app can pass a vacuous one. Reference apps, null controls, and exact seeded mutations are all required.

Inconclusive is not failure

If the harness could not observe a transport, acquire a resource, or keep a browser alive, that absence of evidence cannot become an application defect or a point. Outcomes are now structured separately.

Isolation is an integrity feature

The agent once read the answer key through ordinary file search. Docker-only generation, isolated grader inputs, exact backend leases, and secret-safe artifacts are part of measurement correctness—not deployment polish.

Benchmarking can be product discovery

The strongest output was not a score: failing first-try guarantees and cost traces led to a real reconnect identity defect, while unchanged Docker reproduction isolated a separate development log-authorization defect.

Recommended path from here

We can now choose the build brief and test list independently. The next work is to prove the shared checks on all three stacks, lock the exact run setup, and run enough complete attempts to measure normal variation.

1

Prove the checks

Run every shared quality check against known-good, blank, and deliberately broken apps on MongoDB, PostgreSQL, and SpacetimeDB.

2

Lock the setup

Save the exact product features, quality checks, backend guidance, repair rules, model adapter, and Docker image that define the comparison.

3

Run repeated comparisons

Run several complete attempts per stack and publish the variation, incomplete-run rate, raw evidence, cost, and limitations.

The meeting decision Agree that v1 is a reproducible testing product—not “all five levels.” The finish line is: configurable build briefs and checks, one Docker path, structured evidence, versioned backend and model support, setup checks, and repeated L1/L2 campaigns whose raw results can be independently inspected.
